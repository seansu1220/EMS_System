## 0. 通則（所有小工具共用）

### 0.1 定位
- 位置：`tools/<工具名>/`，是**獨立於網頁系統的本機 CLI**。
- **不參與 `npm run build`、不部署上線**（`tsconfig` 只涵蓋 `src` 與 `vite.config.ts`）。
- 網頁的 `/tools` 頁只放使用說明，不呈現也不儲存任何查詢結果。

### 0.2 為什麼不做在網頁上
瀏覽器的同源政策禁止網站登入並讀取另一個網域的內容，因此網頁**在技術上無法**
代為登入外部系統、處理驗證碼或下載檔案。唯一繞法是架伺服器代抓，
但那會讓個案明細經過雲端主機，與個資要求牴觸，故不採用。

> 同理，手機（iOS）上也不可能直接執行這些工具。若要用手機遠端操作，只能讓
> **手機當遙控器、電腦當實際執行者**——構想與取捨見 [TODO.md](TODO.md) 第 1 節（尚未實作）。

### 0.3 個資保護總則
凡工具會接觸到含個人資料的檔案，一律遵守：

| 規範 | 作法 |
| --- | --- |
| 不上雲 | 全程本機執行；不寫入 Firestore、不呼叫任何外部 API、不上傳檔案（**唯一例外見下方「線上解鎖工單」**） |
| 原始明細用完即刪 | 只落在該工具的 `out/raw/`，統計後自動刪除（`--keep-raw` 才保留） |
| 產出只有統計數字 | 最終報表不含任何個人欄位 |
| 不進版控 | `.gitignore` 已排除 `tools/**/out/` |
| log 不印明細 | 只記錄流程、筆數與**欄位名稱**（欄名屬檔案結構，非個人資料） |
| 探測模式不取資料 | 只記錄欄位／按鈕／下拉選項名稱；資料列表（列數 > 5 的表格）內元素一律跳過；5 碼以上連續數字遮蔽；不截圖 |
| 驗證碼不自動破解 | 由使用者本人辨識輸入，不繞過來源系統的防自動化機制（**不做 OCR、不接第三方辨識服務**） |
| 帳密不硬寫 | 僅從該工具目錄的 `.env` 讀取（已 gitignore），且**禁用 `VITE_` 前綴**以免被打包進前端 |
| 登入狀態視同憑證 | 保存的 cookie 只寫到 `tools/ems-report/.auth/`（已 gitignore、不打包進可攜版），逾期即不再沿用（見 0.8） |

#### 「不上雲」的唯一例外：線上解鎖工單（v1.17 起）

這是為了讓各分隊能自己提出解鎖申請而做的**明確讓步**，不是疏忽，因此寫在這裡而不是藏在章節裡：

| 項目 | 說明 |
| --- | --- |
| **會上雲的** | TEMSIS 編號、申請事由、申請人、解鎖結果說明（案件日期／出勤車輛／狀態） |
| **不會上雲的** | 救護系統的帳密與登入狀態、紀錄表全文、PDF、任何病患資料、任何匯出明細 |
| 為什麼非得放完整編號 | 本機工具要拿它回系統查案件，遮蔽值查不到東西 |
| 誰讀得到 | 已核准的帳號；**「解鎖專用」帳號只讀得到自己送的那幾筆**（Firestore 規則強制） |
| 保存期限 | **永久保留**（使用者 2026-08-06 決定：要留完整的解鎖歷史紀錄可回頭查） |
| 實際連線仍在本機 | 雲端只當「信箱」，連 `emsdt.tyfd.gov.tw` 的仍然是這台電腦（見第 4 章） |

> 原始構想（`docs/TODO.md` 1.7）曾規劃「工作單完成後即刪或設短 TTL」，
> 但使用者 2026-08-06 選擇永久保留——這份紀錄的用途本來就包含事後追查
> 「某件案子什麼時候、被誰申請解鎖」。取捨已知並被接受。

### 0.4 執行方式
**一般使用一律雙擊 `捷徑/` 資料夾內的批次檔，不需輸入任何指令。**

`捷徑/` 只放**日常會用到的**（月度報表輸出／救護預警統計／解鎖試跑／正式解鎖／設定登入帳密）；
偶爾才用的收在 `捷徑/不常用/`（心電圖試跑 5 件、打包可攜版、頁面結構探測、檢查增減試算表），
同資料夾內附 `說明.txt` 交代各自用途。

> 每月的例行工作就是 **`月度報表輸出.bat`**：一次登入把第 1 章與第 3 章兩份報表都做完。
> 只要其中一份時才用 `救護預警統計.bat`。

⚠ **搬動批次檔就要改裡面的相對路徑**：批次檔靠 `cd /d "%~dp0.."` 回到專案根目錄，
多包一層資料夾就得寫成 `"%~dp0..\.."`（`建立可攜版.bat` 內呼叫 `.ps1` 的那行同理）。
批次檔會先確認 Node.js 是否存在（沒有就顯示官網下載連結），並在缺少套件時自動 `npm install`；
內容維持純 ASCII 訊息，避免主控台中文亂碼。

> ⚠ **`.bat` 內絕對不能出現中文，連 `rem` 註解也不行**（2026-07-31 實際踩到）。
> 主控台是 DBCS 代碼頁（cp950），UTF-8 的中文位元組會被當成 Big5 的前導位元組，
> **把後面的字元連同換行一起吃掉**，於是 `if (...)` 區塊被切碎、殘餘片段被當成指令執行，
> 畫面上出現一整串「'ut' 不是內部或外部命令」這種看不出原因的錯誤。
> 需要中文說明就寫在 README 或網頁的 `/tools` 頁，不要寫進批次檔。
>
> ⚠ **含中文的 `.ps1` 必須存成「UTF-8 with BOM」**：Windows PowerShell 5.1
> 讀沒有 BOM 的檔案時會用系統 ANSI 代碼頁解碼，中文會變亂碼（連字串內的路徑也會壞掉）。

### 0.7 終端機輸入與「一次貼上多行」（踩過的坑）
使用者的真實用法是從 Excel 複製**一整欄**號碼，直接貼進黑色視窗。這牽涉兩層：

| 層 | 現象與作法 |
| --- | --- |
| Windows 主控台 | CMD 的 `Ctrl+V` 常被中文輸入法攔走而沒反應；**在視窗內按滑鼠右鍵**即為貼上（快速編輯模式預設開啟）。提示文字已同時寫在 `.bat` 與程式的說明列。 |
| 程式（`logger.mjs`） | `readline` 在**沒有 `question()` 在等待**時仍會照常讀走輸入並發出 `line` 事件，沒人接就直接消失。一次貼多行時，第一行被 `question()` 收走，其餘行落在兩次 `question()` 之間而**整批遺失**——畫面看起來就像「貼不上去」。 |

另有一個純顯示的坑：**按下 Enter 後，剛輸入的那行會從畫面上消失**（值有讀到，只是看不見）。
conhost 上 readline 會依提示字寬重繪該行，提示含全形字或整行過長時就會把內容抹掉。
因此互動提示一律維持**短且純 ASCII**（`  [1] `），中文說明另外用獨立行印，
並在每收到一筆後補印「已收到 N 筆」當回條。

作法：`logger.mjs` 提供 `startLineBuffering()` / `stopLineBuffering()`，
開啟期間所有 `line` 事件都存進佇列，`prompt()` 一律**先取佇列**再等新輸入
（EOF 後也要先把佇列清完，否則整段一次灌入時會被誤判成沒輸入）。

只在「連續讀取多行」的情境開啟（目前僅 `promptTemsisList()`），
其餘等待單一按鍵處維持不緩衝——否則使用者在等待登入時誤按的 Enter 會被留到後面才生效。

### 0.8 登入狀態保存（免每一輪都重打驗證碼）

**動機**：驗證碼一律由本人辨識（0.3），但一天要跑好幾輪時等於每輪都得重打一次。

**作法**：本人登入成功後，把該工作階段（cookie）存成 `tools/ems-report/.auth/state.json`；
下一輪啟動時以 `browser.newContext({ storageState })` 帶入，系統看到已登入就不會出現登入頁。

> ⚠ **這不是繞過驗證碼**：驗證碼仍由使用者本人解過一次，這裡只是沿用自己解出來的登入結果，
> 等同瀏覽器的「保持登入」。**不做 OCR、不接辨識服務**的原則不因本節而鬆動。

| 環節 | 規則 |
| --- | --- |
| 判定沿用成功 | 進站後「登入頁沒出現」**且**主畫面 frameset 建得起來，兩者都成立才算數 |
| 沿用的試探逾時 | `SESSION_STATE.reuseReadyTimeoutMs`＝15 秒（刻意遠短於正常登入的 60 秒；這是試探，失敗只是退回登入，不值得空等） |
| 沿用失敗 | 一律**安靜退回正常登入**：刪掉舊檔、重新進站、走原本的代填帳密＋本人輸入驗證碼 |
| 本機保存期限 | `SESSION_STATE.maxAgeMs`＝8 小時。伺服器通常更早就讓 session 過期（過期會自動退回登入頁），設上限只是不讓憑證無限期留在磁碟上 |
| 何時寫檔 | 登入成功後寫一次；**流程結束關閉瀏覽器前再寫一次**（cookie 可能在這一輪被伺服器換過） |
| 寫檔失敗 | 只警告不中斷——後果僅是下次要重打驗證碼，不該讓已經跑起來的流程掛掉 |
| 強制重登 | 任何指令加 `--fresh-login`（`startSession({ freshLogin: true })`） |

檔案內容等同登入憑證，故 `.gitignore` 已加 `tools/**/.auth/`，可攜版也不會複製。

## 1. 救護紀錄表查詢（到院前預警比率）

位置：`tools/ems-report/`

### 1.1 目的
自「桃園市政府消防局緊急救護管理系統」（`https://emsdt.tyfd.gov.tw/EmmWeb/`）
取得指定月份的救護紀錄，統計**各分隊的「到院前預警案件數 ÷ 總案件數」比率**。

### 1.2 執行方式

| `不常用/救護預警統計-設定用.bat` | 頁面結構探測，系統改版時才用 |

### 1.3 自動化流程
1. 開啟登入頁；**若上次的登入狀態還有效就直接沿用、跳過這一步**（見 0.8）。
   需要登入時：帳密可自 `.env` 代填，**驗證碼由使用者在瀏覽器輸入**。
   程式輪詢等待登入完成，再等 `contentSidemenu`／`contentFrame` 兩個 frame 真正出現才續行。
2. 左側選單 → 報表系統 → 救護紀錄表查詢。
3. 填入共同查詢條件，**填完一律回讀驗證**：
   - 查詢期間（起日 `00:00:00`、迄日 `23:59:59`）
   - 救護狀態＝「已結案」
   - **送醫情形＝「送醫」**（未運送案件如誤報、拒送、現場死亡不會有到院前預警，
     算進母數會稀釋比率）
4. 院前預警不設限 → 查詢 → 匯出 Excel（**總案件數**）。
5. 院前預警＝「到院前傳送預警」→ 查詢 → 匯出 Excel（**預警案件數**）。
6. 本機解析兩份 Excel，依分隊彙總。
7. 讀取增減試算表，扣除期間內應排除的案件（見 1.7）。
8. 輸出兩個分頁的報表後刪除原始明細。

彈出式視窗封鎖不需另外處理：自動化瀏覽器預設允許彈出視窗與檔案下載。

### 1.6 報表格式

> **版面共用、內容分兩份**（v1.16.0 起）：本章與第 3 章的報表長得一模一樣，
> 差別只有標題與欄名。因此樣式集中在 `REPORT_FORMAT`（字級、框線、大隊列底色…），
> 「這份報表叫什麼、欄位怎麼命名」則放在 `REPORT_PROFILES.alert` / `.ekg`。
> 改版面兩份一起變，改欄名只動其中一份。
> 比率欄一律是**最後一欄**（不寫死第 4 欄），欄數日後不同也不會錯位。

比照使用者既有的人工報表（`6月份到院前預警比例.xlsx`），輸出**兩個分頁**：

| 分頁 | 內容 |
| --- | --- |
| `到院前預警比例` | 各大隊合計列 ＋ 其轄下分隊（依 `BRIGADES` 設定的官方順序） |
| `排序` | 各分隊依**到院前預警率由高到低** |

兩個分頁格式相同：
- 第 1 列為標題並跨 4 欄合併，內容為 `本局{起}-{迄}{後綴}`（例：`本局6/1-6/30到院前預警案件執行率`）。
  **後綴以數字開頭時中間補一個半形空格**（2026-08-11 加）：心電圖那份的後綴是「12導程…」，
  直接接上去會變成 `本局7/1-7/3112導程心電圖…`，日期與後綴糊成一團看不懂。
  後綴是中文開頭的則不加，維持既有報表原本的樣子。
- 第 2 列欄位標題：（留白）｜`有送醫有預警案件`｜`有送醫案件`｜`到院前預警率`
- 比率欄以數值寫入並套 `0.00%` 格式，可直接在 Excel 內再排序或製圖
- **大隊列為紅底深紅粗體字**（`REPORT_FORMAT.brigadeRowStyle`，色碼可自行調整），
  一眼即可與轄下分隊區分；`排序`分頁只有分隊，故無上色
- **每一格四邊皆有 `thin` 框線、文字水平垂直置中**
- **字級：內文 12、第一列標題 16**；列高設為約字級的兩倍（標題 32、其餘 24），留出上下空白避免擁擠
- **欄寬依內容自動計算**（中日韓字元以兩倍寬計，再乘字級比例並加邊距），
  `columnWidths` 僅作為下限，確保文字不會被截斷

> 報表檔若正被 Excel 開啟會無法覆寫（EBUSY/EPERM），此時輸出明確的中文提示
> 並說明查詢結果不需重跑、只差寫檔這一步。

> **輸出用 ExcelJS 而非 SheetJS**：SheetJS 的免費版**不會寫入儲存格底色**
> （樣式屬付費功能，寫進去讀回來會變成 `patternType: none`）。
> 讀取匯出檔仍用 SheetJS，因為 ExcelJS 不支援舊的 `.xls` 格式。

大隊與轄下分隊的對應表定義於 `config.mjs` 的 `BRIGADES`（4 大隊、41 分隊），
順序取自既有報表。匯出檔中出現但不在對應表內的單位會歸入「未對應大隊」並在紀錄檔提出警告，
**不會被默默丟掉**。

### 1.7 統計規則
- **分隊欄位以「內容」判定而非欄名**：值以「分隊／大隊／中隊」結尾的比例達 80% 以上者即為分隊欄。
  內容判斷不出來時才退回欄名比對（`SQUAD_COLUMN_CANDIDATES`），且「包含」比對取最短欄名。
- 分隊比率＝該分隊預警案件數 ÷ 該分隊送醫案件數；送醫案件為 0 時比率為 `null`（不做除以零）。
- **大隊比率＝該大隊預警案件總數 ÷ 送醫案件總數（加權）**，使用者於 2026-07-28 確認採此算法。
  ⚠ 使用者先前的人工報表取的是「各分隊比率的平均」，兩者相差約 0.2~1.0 個百分點
  （案件量小的分隊在平均法中權重被放大），故新舊報表的大隊數字不會完全相同，屬預期差異。
- `排序`分頁依預警率由高到低；比率相同時案件多的在前，再相同則依名稱，確保輸出順序穩定。
- **合理性檢查**：資料超過 100 筆卻只分出少於 3 個分隊時直接中止並列出實際欄名，
  避免產出明顯錯誤的報表。
- 解析失敗時**保留原始檔**並輸出「只有欄名與筆數」的診斷資訊，不輸出任何資料格內容。

#### 增減試算表的扣除規則（v1.11.6 起）
使用者維護一份 Google 試算表，列出應自統計中排除的案件。規則（2026-07-28 確認）：

- 讀**第一個分頁**（`EMS_ADJUST_SHEET_GID` 留白即為第一個分頁）。
- 每一列代表一件應排除的案件；**日期落在查詢期間內**者才計入。
- **只扣該分隊的送醫案件數（分母），預警案件數（分子）不動**
  ——把這些案件排除在評比之外。使用者於 2026-07-29 再次確認採此算法。
  ⚠ **與 6 月以前的人工報表口徑不同**：舊報表是把同一批案件**加到分子**

## 2. 解鎖救護紀錄表

位置：`tools/ems-report/`（與第 1 章同一個工具，共用登入與導航模組）

### 2.1 目的
把指定 TEMSIS 的案件由「已結案」調整為「未結案」。人工流程一筆要在四個畫面之間來回，
多筆時非常耗時，且案件內有多張紀錄表時容易解錯張。

### 2.2 執行模式與安全設計
**預設是試跑（只定位不動手）**，要真的解鎖必須明確加 `--execute`。
解鎖無法復原，預設值就該站在安全的那一邊。

2026-08-02 試跑連續驗證通過（兩筆都正確定位、日期與車輛都讀到）後，
使用者決定**開放正式解鎖**，並明確指定：

- **中途不要攔他確認**（比對完就直接按下去），
- 但**結束時要單獨列出「這次到底動了哪幾件」**：案件日期時間＋車輛（分隊）＋第幾張紀錄表。

因此正式模式另做一個捷徑（見 2.3），試跑仍是指令列的預設值。
誤點正式捷徑不會有事：**沒貼 TEMSIS、沒登入就什麼都不會發生**，直接關掉即可。

解鎖不可復原，因此安全設計全部押在「**不確定就不動手**」：

| 情況 | 行為 |
| --- | --- |
| 明確定位到唯一相符的紀錄表 | 按下該列的「調整為未結案」 |
| 比對不到相符的 TEMSIS | **略過**，回報需人工處理 |
| 有鎖頭的都比對過都不相符、其餘本來就沒鎖 | 回報 **`無需處理`**（不是失敗）——案號是用這個 TEMSIS 查出來的，案件不會錯，所以要找的那張只可能落在沒鎖的那幾張裡 |
| 多張紀錄表的 TEMSIS 都相符 | **略過**（代表比對有問題，例如序號沒生效） |
| 相符那一列沒有解鎖按鈕 | **略過**（不靠序號猜按鈕） |
| 查無案件、讀不到案號 | **略過**，該筆標記失敗，不影響其他筆 |

其他保護：
- **確認視窗必須自己接手**：Playwright 預設會自動按「取消」，
  不註冊 dialog 處理就會靜靜地什麼都沒解到、卻看起來像成功。
- **解完回讀驗證：看兩個訊號，任一成立就算解開了**：

  | 訊號 | 依據 |
  | --- | --- |
  | 畫面出現「已修改為未結案並解鎖」 | 系統自己說的，最直接（`UNLOCK.successMarkers`） |
  | **按下去的那一列**由「救護紀錄**(鎖)**」變成「救護紀錄」 | 以**解鎖按鈕的序號**當錨點找同一列（`findPairedRows`） |

  訊息必須是**按下之後才新出現的**才算數（按之前先記一次基準），畫面上本來就有的不列入
  ——不然上一件解鎖留在畫面上的訊息會讓下一件誤判成功。
  訊息可能出現在 header frame 也可能在內容框最上方，故**逐個 frame 找**，不預設在哪一個。

  鎖頭要比對**同一列**而不是全頁鎖頭總數：總數變少只能說明「有某張被解開」，
  不能說明解開的是不是你按的那張。按完之後讀不到那一列（畫面被導走）時 `after` 為 `null`，
  一律不算成功——不知道不等於成功。

  > ⚠ **刻意不看「解鎖按鈕有沒有變少」**（2026-08-06 移除）。使用者確認那個按鈕
  > **解完之後永遠不會消失**，所以它驗不到任何東西，還會反過來製造誤判：
  > 萬一按下去之後畫面被導走（逾時、跳錯誤頁），按鈕數會從 N 掉到 0，
  > 「變少了」於是成立，一件根本沒解到的案子會被報成已解鎖。

  > 2026-08-05 使用者回報：實際已正確解鎖，程式卻回報「無法確認是否生效」。
  > 原因正是舊版只看解鎖按鈕數量。使用者描述的成功畫面（那一列鎖頭消失＋左上角紅字）
  > 因此升格為正式的判斷依據。

  兩個訊號都沒動時仍回報「已按下但無法確認是否生效，請自行到系統確認」，
  並把兩項分別是什麼狀況寫進說明，一看就知道要調哪個設定。
- **每筆都記下案件日期與出勤車輛**（使用者指定），寫入 `out/last-run.log`，
  這是事後回頭查「到底解了哪些案件」的唯一依據。
  這兩個欄位是案件的行政資訊（非民眾個資），且只落在本機紀錄檔。
- **結束時單獨列出解鎖清單**（`printUnlockedList()`）：只列真的按下去的那幾筆，
  格式為「日期時間　車輛（分隊）　第 N 張紀錄表　TEMSIS 末 4 碼」。
  上方那張總表混著各種狀態、說明又長，動過的幾筆容易被淹沒，故另列一張。

### 2.3 執行方式
| 捷徑 | 用途 |
| --- | --- |
| `解鎖救護紀錄表.bat` | **試跑**：只找出該解哪一張，不動系統資料 |
| `正式解鎖救護紀錄表.bat` | **正式**：真的按下「調整為未結案」，結束時列出解鎖清單 |
| `不常用/建立可攜版.bat` | 打包成隨身版，給不能安裝 Node.js 的電腦（見 0.6） |

指令列等價寫法：

| 指令 | 用途 |
| --- | --- |
| `npm run tool:ems -- unlock` | **試跑**：貼上 TEMSIS（可整欄一次貼上，空白行結束），只回報不動手 |
| `npm run tool:ems -- unlock --execute` | 真的按下「調整為未結案」 |
| `npm run tool:ems -- unlock --temsis=A,B` | 直接指定，省去互動輸入 |

TEMSIS 一行可貼多個（以空白、逗號、分號分隔），也可以一次貼上整欄多行
（見 0.7 的輸入行緩衝），重複的會自動去除。

### 2.4 自動化流程（每一筆 TEMSIS 各跑一輪）
1. 報表系統 → 救護紀錄表查詢；查詢期間設為**今天往回推兩個月**（`UNLOCK.lookbackMonths`）。
2. 填入 TEMSIS → 查詢。
3. 點該列的「救護紀錄PDF」，讀出**救災救護指揮中心指派案號**。
   同時讀出紀錄表上的 TEMSIS 與輸入值比對，**不符即中止**（防止查詢條件沒生效）。
4. 報表系統 → 案件列表；期間同樣近兩個月，填入派遣案號 → 查詢。
5. 點「救護紀錄」進入案件內部。
6. 決定目標：
   - 只有一個「調整為未結案」按鈕 → 該張即為目標。
   - 有多張 → **逐張開啟紀錄表比對 TEMSIS**（全部掃過，不是找到就停），
     只有唯一相符那張所在列的按鈕才是目標。
   - 比對不到、多張都相符、或相符那列沒有按鈕 → 回報「需人工處理」，**絕不挑一張**。
   - **沒有鎖頭的那張**（按鈕文字是 `救護紀錄` 而非 `救護紀錄(鎖)`）→ 已是未結案，
     不是解鎖目標，**略過不點**（見 2.5）；這些張數不影響能不能動手，但要在說明中交代。
   - **某張把畫面導走**（實測踩到：該張按下去不是另開視窗，而是把案件內部整個換掉）→
     `abortCheckDelayMs` 之後每輪檢查案件內部的特徵字還在不在，一旦消失就立刻收手，
     並**重新進入該案件**再比對下一張。不這麼做的話，後面幾張會在已被換掉的畫面上找按鈕，
     連環回報「找不到按鈕，畫面可能已改版」這種與事實無關的訊息，連出勤車輛也讀不到。
     回不去案件內部時，其餘各張記為「沒有比對到」，**不可記成「不相符」**。
     被導走時會記下該畫面可點的東西並存快照（`解鎖-紀錄表把畫面導走`），供追查原因。
     **打不開與第幾張無關**（實測：另一件案子的第 2 張正常開啟且正是目標），是那一張本身的差異。
   - **打得開的都不相符、且只剩一張沒掃到** → 明講「你要的很可能就是第 N 張」，
     但仍不動手：沒親眼比對過就不算數。
   - **某張打不開**（點了沒出現紀錄表，或系統跳訊息擋下）→ 不讓整筆失敗，
     記下來繼續掃其餘各張；最後即使有唯一相符的一張，也因為「無法確認打不開的那張是否也相符」
     而回報「需人工處理」，不自動解鎖。已比對出的線索（第幾張相符、日期、出勤車輛）照常保留，
     使用者才有辦法接手人工核對。
7. 按下該按鈕（**只有 `--execute` 時才做**），處理確認視窗，再依上述兩個訊號確認真的解開了。
8. 印出每一筆的結果摘要（狀態＋案件日期＋出勤車輛＋原因）。

**狀態一覽**（`UnlockOutcome.status`）：

| 狀態 | 意思 | 摘要怎麼算 |
| --- | --- | --- |
| `已解鎖` | 真的按下去且驗證通過 | 已解鎖 N 筆 |
| `已定位` | 試跑模式找到目標，沒有動手 | 定位成功 N 筆 |
| `無需處理` | 那張**本來就沒有鎖頭**（已是未結案） | 本來就沒鎖 N 筆（不需動作） |
| `需人工處理` | **程式判斷不出來**，要人接手 | 需要你接手 N 筆 |
| `查無案件`／`失敗` | 查不到或流程出錯 | 併入「需要你接手」 |

> ⚠ **`無需處理` 必須與 `需人工處理` 分開**（使用者 2026-08-06 指正）。
> 舊版把「本來就沒鎖」也算成未處理，於是一次 4 筆全部順利的執行被寫成
> 「已解鎖 3 筆、未處理 1 筆」，看起來像是有一筆出了問題。
> `無需處理` 在紀錄裡也改用一般訊息（不是警告）呈現，收尾也不會叫使用者去人工處理。

### 2.5 定位方式：以畫面文字，不靠 id
解鎖流程走的畫面沒有探測過，拿不到 id；且系統改版時 id 會變、畫面文字不太會變。
因此 `pageFinder.mjs` 改用近似人眼的方式定位：

| 要找的東西 | 作法 |
| --- | --- |
| 輸入欄 | 找到含標籤文字的儲存格 → 取**同列下一個儲存格**內的輸入欄（依序再試 `label[for]`、同列、父層容器） |
| 按鈕／連結 | 比對元素的文字、`alt`、`title`、`value`（舊系統的按鈕多是 `<img>`） |
| 「這是第幾筆案件」 | 依所在 `<tr>` 分組（同一列的多個按鈕屬同一筆，直接數按鈕會變兩倍） |
| 「這個解鎖按鈕屬於哪張紀錄表」 | **同一個 `<tr>`**（序號配對不安全，順序未必一致） |
| 「動作到底有沒有生效」 | 找**畫面上的系統訊息**（`findPageMarker`），例如解鎖後那行「已修改為未結案並解鎖」。只回傳命中的字樣與那一行文字，長數字已遮蔽 |

比對前一律正規化（去空白與 `：*、,．` 等標點、轉大寫），因為舊系統的標籤常寫成
「T E M S I S 編號：」這種形式。

**`exact` 必須前後一致**：算出序號時與點擊時若一邊用完全相等、一邊用包含比對，
兩邊的符合集合不同，序號就會對到別張紀錄表。`救護紀錄` 用完全相等
（否則會連 `救護紀錄PDF` 一起命中），`救護紀錄PDF` 用包含（要同時吃到 `(桃)` 版）。

**案件內部的紀錄表按鈕有兩種，差一個鎖頭**（2026-08-02 實測確認，同一件案子裡混用）：

| 按鈕文字 | 意義 | 點下去會怎樣 |
| --- | --- | --- |
| `救護紀錄(鎖)` | 已結案、鎖住 | 另開視窗顯示 PDF ← **只有這種才是解鎖目標** |
| `救護紀錄` | 尚未結案 | 進入紀錄表**編輯畫面**（新增／修改／儲存／匯出Pdf），不會有 PDF |

沒鎖頭那張既然已是未結案，就不可能是解鎖目標，逐張比對時**直接略過不點**
（`UNLOCK.buttonTexts.lockedRecordMarker`）。不略過的話會被帶進編輯畫面、
接著還得重新進入案件，白繞一大圈。
判斷只比對「鎖」字，避免被全形／半形括號差異絆倒；
**讀不到按鈕文字時一律當成鎖住的**，寧可多開一張，也不要把真正的目標略過。

### 2.6 救護紀錄表的讀取
系統可能用三種方式呈現，`recordSheet.mjs` 三種都處理：

| 呈現方式 | 取得內容的作法 |
| --- | --- |
| 另開視窗顯示 PDF | 監聽回應，`content-type` 為 `application/pdf` 時取其位元組 |
| Chrome 內建閱讀器（DOM 讀不到） | 以同一登入狀態 `context.request.get()` 取回該網址 |
| 直接觸發下載 | 讀下載串流（**不落檔**） |
| 一般網頁 | 直接讀 `innerText` |

PDF 以 `pdfjs-dist` 轉文字，並指向套件內附的 `cmaps`／`standard_fonts`
（中文 PDF 多用 CID 字型，缺了會抽出亂碼），全程離線。

**必須自己接手 `dialog` 事件**：系統用 `alert`／`confirm` 擋下時
（例如某張紀錄表根本開不出來），Playwright 預設會自動關掉且不留任何痕跡，
程式只會傻等到逾時，事後完全看不出系統其實有回話。
`openRecordSheet()` 因此監聽 `dialog`，把訊息（長數字遮蔽後）記進紀錄檔並立刻結束等待。
動作維持預設的「關閉／取消」——這裡只是唯讀地開紀錄表，
按下確定有可能觸發沒預期的動作，寧可如實記下訊息交給人判斷。

欄位擷取（`sheetFields.mjs`，純函式）：把文字壓掉空白後找標籤，再回到原文取標籤後方
第一段編號樣式的字串。**找不到就回傳 null，不猜值**。

### 2.7 個資保護（本流程特別注意）
| 規範 | 作法 |

| 快照沿用探測規則 | 只記結構，資料列（列數 > 5 的表格）內元素一律跳過 |

## 3. 12 導程心電圖到院前傳輸率

位置：`tools/ems-report/`（與第 1、2 章同一個工具，共用登入、導航與報表模組）

### 3.1 目的
統計各分隊「**做了 12 導程心電圖，而且在到院前就傳出去**」的比率。

| | 定義 |
| --- | --- |
| 分母 | 期間內**有勾 EKG 檢查「或」有 12 導程心電圖**的案件數（**聯集**，同一件只算一次） |
| 分子 | 期間內做了 **12 導程心電圖**，且經逐案查核確認**上傳時間早於到院時間**的案件數 |

> **分母為什麼取聯集**（使用者 2026-08-04 決定）：實測兩個條件**互有出入、誰都不是誰的子集合**
> ——有勾 EKG檢查 243 件、有 12 導程 285 件、交集只有 202 件。
> 用任一邊當分母都會把另一邊獨有的案件排除在評比之外（83 件有做卻沒勾、41 件勾了卻沒傳）。
> 系統的查詢條件做不出 OR，因此**在本機以 TEMSIS 去重取聯集**（`countUnionBySquad`）。
> 分子取自 12 導程那一份，整份都在聯集裡，所以**比率必定 ≤ 100%**。

系統的查詢只告訴你「有沒有做 12 導程」，不告訴你「什麼時候傳出去的」，
因此分子必須一件一件點開查核——這是本章最花時間、也最容易出錯的部分（見 3.4）。

### 3.2 查詢條件
**兩次查詢都設「救護狀態＝已結案、送醫情形＝送醫」**（使用者 2026-08-05 決定，
設定在 `EKG.baseCriteria`），與第 1 章同一組代碼、同一個口徑。

> 原本兩個都不限（2026-08-03 的決定）。改的理由不是數字差很多——實測
> 勾EKG檢查 243→242、12導程 285→284，**各只少 1 件**——而是那一件正好是
> 待人工確認清單上**唯一的資料問題**：它沒有送醫，所以沒有「送達醫院時間」
> 可以拿來比對，只能判「無法判定」。加了條件就直接把它排除在母體外。

| 次序 | 條件 | 產出 |
| --- | --- | --- |
| 1 | 勾選「EKG檢查」、心電圖下拉清空 | 分母 |
| 2 | 取消「EKG檢查」、心電圖下拉＝「12導程心電圖」 | 分子（未查核） |

> 兩次之間**明確把上一次的條件清掉**，而不是假設「重新載入應該是空的」——
> 頁面在兩次查詢之間不會重載，上次選過的值會留著。

> 分子要不要一起勾著「EKG檢查」由 `EKG.keepProcedureCheckedForNumerator` 控制，
> 預設 `false`（照使用者描述的操作）。12 導程本來就是 EKG 的一種，理論上勾不勾結果相同。

**自動防呆**：任何分隊的分子大於分母就**大聲警告**。
12 導程是 EKG 的子集合，分子不可能比較多；出現這種情形代表兩個欄位的語意
與我們的假設不同（最可能是「EKG檢查」勾選框抓錯欄位）。
這是唯一能自動抓出「條件不一致」的檢查點——這種錯誤產出的報表看起來完全正常。

### 3.3 欄位怎麼定位（都沒有探測過）
「EKG檢查」勾選框與「心電圖」下拉**都不在既有的探測結果裡**
（探測檔只有 22 個下拉，沒有心電圖；400 多個勾選框的 id 全是 `_scarcbc040102` 這種代碼）。
因此一律以畫面文字定位：

| 目標 | 作法 |
| --- | --- |
| EKG檢查勾選框 | 比對**勾選框旁邊的文字**（`EKG.procedureLabels`） |
| 心電圖下拉 | 用**選項文字**反推是哪一個 `<select>`（找含「12導程心電圖」選項的那個） |

用選項反推而不是找標籤，是因為一頁上有 20 幾個下拉，
但「12導程心電圖」這個選項只會出現在唯一一個下拉裡，精確得多，
系統把標籤從「心電圖」改成「心電圖類型」也不受影響。

**勾選框的「距離分級」（實測踩到）**：舊系統的版面是
`<td><input A>氣管內管</td><td><input B>EKG檢查</td>`，
而 A 讀得到隔壁格的「EKG檢查」。若不分距離，A 會因為在 document 中比較前面而搶先命中。
因此比對分數依序看：**候選字樣順序 → 距離（自己的標籤勝過隔壁格）→ 完全相等勝過包含**。

**沒有 id 的勾選框一律不回傳**：這個系統有大量同名的勾選框
（`_scar`、`_nScar` 一組幾十個共用一個 name），用 name 當選擇器會一次選到一整群。

### 3.4 逐案查核（分子的關鍵）
對分子匯出檔的每一件案子各跑一輪：

1. 以 **TEMSIS** 查回該筆案件（TEMSIS 取自匯出檔，找不到該欄就中止並列出實際欄名）
2. 取得**到院時間**，由便宜到昂貴依序試：匯出檔的欄 → 查詢結果那一列 → 救護紀錄表 PDF
3. 讀救護紀錄表 PDF 取得**指派案號** → 案件列表 → 進入案件內部
4. 取得 **12 導程的上傳時間**：
   - **先看案件內部的「上傳」**（一列一個檔案，直接寫著 `檔案類型＝12導程心電圖` 與 `上傳時間`）。
     ⚠ **只比對「檔案類型」欄的值**，不可比對整列文字：同一列的備註寫著
     「ZOLL12導程附檔上傳(JSON檔)」，而別的列可能是「檔案類型＝其他、備註＝12導程操作說明書」，
     比對整列會把後者誤算成有做（使用者 2026-08-05 指正）
   - 上傳清單裡沒有 12 導程時，**才回頭查查詢結果那一列的「傳輸紀錄」**，
     取 **EKG 欄有值那幾列的量測時間**
5. 比較兩個時間

> **順序是使用者 2026-08-04 依實測結果決定的**：上傳為主，沒有才回頭查傳輸紀錄。
> 理由見 3.11——設備自動傳的檔案也會進到上傳清單（備註寫著「ZOLL介接心電圖」），
> 而傳輸紀錄的時間欄是「量測時間」（什麼時候量的），與「什麼時候傳出去」語意不同，
> 故只當後備。走到後備時，待人工確認清單上會註明時間來源是量測時間。

> ⚠ 傳輸紀錄按下去會**把查詢結果整個導走**，所以它排在最後：
> 先走它的話，每一件都要多花 30 秒逾時 ＋ 十幾秒重新查詢（實測全月因此多跑 3~4 小時）。

#### 3.4.1 排除 OHCA 案件（處置勾了 CPR）

**使用者 2026-08-13 決定：處置項目勾了 CPR 的案件，分母與分子都不計入。**
判定規則是使用者給的——**勾了 CPR 就代表那件是 OHCA**。
OHCA 心電圖與 12 導程心電圖是兩回事，不該拿來算 12 導程的到院前傳輸率。

由 `EKG.excludeCprCases` 開關（預設開），CPR 勾選框字樣在 `EKG.cprLabels`。

**做法**：在兩次主查詢之外**多跑一次查詢**——`已結案＋送醫 ＋ 處置勾CPR`，
心電圖**不限**、EKG檢查**不勾**，撈出整月所有 CPR 案件，再與分母取交集後排掉。

> ⚠ 這一次查詢刻意**不加心電圖條件**。分母是聯集，CPR 案件可能是從
> 「勾EKG檢查」那一邊進來的，只查「12導程＋CPR」會漏掉那些。

> ⚠ **CPR 條件每一次查詢都要明講勾或不勾**（`queryAndExport` 的 `extraCheckboxes`）。
> 這系統的查詢條件會殘留，只在要勾的那次傳的話，後面每次查詢都被偷偷多加一個條件，
> 件數全部是錯的。

**排除發生在最前面**：`index.mjs` 的 `applyCprExclusion()` 直接就地改寫
`table.rows`，因此後面每一段（聯集、差集清冊、逐案查核、逐案判定表）自動一致。
不這樣做的話要在十幾個地方各記得過濾一次，漏掉任何一處就會產出
「分母排除了、分子沒排除」這種對不起來的報表。

**排除掉的案件不可以默默消失**，三個地方都看得到：

| 在哪裡 | 怎麼呈現 |
|---|---|
| 終端機 | 件數 ＋ 各分隊件數 |
| 執行報告 | 專章「已排除的案件（處置勾了 CPR ＝ OHCA）」，逐案列出（TEMSIS 末 4 碼） |
| 逐案判定表 | 列在**最前面**，判定寫「排除：處置勾CPR」、計入分子「否」（完整 TEMSIS） |

因此逐案判定表的**列數會多於分母**，差額就是被排除的件數——這是刻意的，
分隊來對數字時第一個要找的就是這些。

判定結果三種：

| 判定 | 處理 |
| --- | --- |
| 到院前 | **計入分子** |
| 到院後 | 不計入（使用者的規則：到院後才傳就不算有做 EKG） |
| 無法判定 | 不計入，**另外列成一張清單交給使用者人工判定**（使用者 2026-08-03 選擇） |

同一件案子傳過好幾次（重傳、補傳）時取**最早**的一次：
只要曾經在到院前傳出去過，就算有做到到院前傳輸。

上傳時間欄的比對**以候選字樣為外層迴圈**，不是以欄位順序：
設定檔把 `上傳時間` 排在 `建立時間`、`時間` 前面就是要讓它優先，
照欄位順序找的話，排在前面的「建立時間」欄會先命中而取到錯的時間
（建立與上傳可能差幾十分鐘，剛好跨過到院時間就整件判反）。

### 3.5 時間比較（`timeParse.mjs`，純函式）
支援的寫法：`2026/07/02 12:44:08`、`2026-07-02 12:44`、`2026年7月2日 12:44`、
民國年 `115/07/02 12:44`、只有月日的 `07-02 07:32`、只有時分的 `12:44`。

設計原則是**看不懂或有歧義就回報「無法判定」，絕不猜**：

| 情況 | 行為 |
| --- | --- |
| 樣式對上但數值不合理（`2026-13-02 12:44`） | 回 `null`，**不往下掉到「只有時分」**——那會安上預設日期而變成憑空捏造的時間 |
| **年份早於 2000（`0001/01/01 00:00:00`）** | 回 `null`——那是系統的**空值哨兵**，不是時間，詳見下方 |
| 只有月日、又沒給年份 | 回 `null` |
| 兩邊都只有時分、且相差超過 12 小時 | **無法判定**（可能跨日：23:50 上傳、隔天 00:30 到院，硬比會得出完全相反的結論） |
| 兩個時間完全相同 | 無法判定，交給人看 |

> ⚠ **`0001/01/01 00:00:00` 是「這一欄沒填」，不是一個時間**（2026-08-11 實跑踩到）。
> 系統的到院時間欄沒填時，匯出檔寫的不是空白，而是 .NET 的 `DateTime.MinValue`。
> 它長得完全像合法日期，年份只有 1 位數還會被當成**民國 1 年**換算成 1912，
> 於是「上傳時間晚於 1912 年」永遠成立——整件被判成**到院後**，分隊白白掉一件。
> 七月只有三民 7/12 那一件踩到，但只要有一件就足以讓一個分隊的比率從 50% 掉到 25%。
>
> 因此 `parseDateTime` 的年份下限為 `EARLIEST_PLAUSIBLE_YEAR = 2000`，
> 低於它一律回 `null`（＝讀不到）。回 null 之後呼叫端才會往下一個來源
> （查詢結果那一列 → 救護紀錄表 PDF）找真正的到院時間；
> 真的都沒有才列入人工確認，而不是給一個錯的結論。

### 3.6 為什麼要能「中斷續跑」
一件要開好幾個畫面，幾百件就是一兩個小時。因此：

- **每完成一件就寫一次進度檔**（`out/internal/心電圖查核進度-{YYYY-MM}.json`），
  中途關掉視窗、當機、網路斷線都不必從頭跑，再執行一次會接著跑。
  - 2026-08-10 起**不再跑完就刪**（原本放 `out/raw/`，與匯出檔一起清掉）：
    刪掉的話補一筆申訴、修好一個讀取問題都得重跑一兩個小時，
    而逐案判定表本來就留著同樣的 TEMSIS 與時間，刪這一份並沒有多保護到什麼。
    改與其他產出一起用三個月的保留期限（見 3.15）。
  - **續跑只跳過有結論的（到院前／到院後）**；`無法判定` 會重新查一遍——
    那多半是暫時性失敗，舊版連它一起跳過，等於把一次失敗永久固定下來，
    連程式修好了都救不回，只能整月重跑。
- **「以 TEMSIS 查不到案件」算暫時性失敗、會重試**（2026-08-10 改）：
  待查核的 TEMSIS 全部來自同一次匯出檔，系統裡一定有，查不到就是查詢頁還沒就緒。
  舊版直接判成「無法判定（可能已被修改或刪除）」，實跑一次就有 4 件誤判。
- **連續 5 件判定不出來就中止**（`EKG.verify.abortAfterConsecutiveFailures`）：
  畫面改版時每一件都會失敗，跑滿兩小時只是浪費，早點停下來讓人看錯誤訊息。
  已完成的進度照樣保留。
- `--limit=N` 先試跑幾件（`不常用/心電圖傳輸統計-試跑5件.bat`），
  確認到院時間與上傳時間都讀對了再跑整個月。
- `--squad=平鎮分隊` **只查核某一分隊**，並把每一件的判定逐件印出來
  （案件日期／TEMSIS 末 4 碼／到院時間／上傳時間／判定與依據，**到院後與判不出來的排前面**）。
  分隊拿自己的數字來對時用：重跑整月要一兩個小時，要看的往往只有那幾件。
- `--no-verify` 跳過查核只看原始件數（很快），用來確認查詢條件抓對了沒。
  **這種數字不是正式報表**：沒有排除掉到院後才上傳的案件，會偏高，程式也會這樣警告。

> ⚠ `--squad` 是**診斷用途**：查核範圍不完整，因此比照 `--limit`／`--no-verify`
> **不寫出正式報表**，而且**不寫「待人工確認清單」**——那份是整月的，
> 只查一個分隊時寫出去會把整月那份蓋成殘缺版本。
> 分隊名稱打錯會**直接中止並列出實際有的分隊**：不擋的話會安靜地查核 0 件，
> 跑完只說「到院前傳出 0 件」，看起來像是那個分隊真的一件都沒有。

#### 3.7.1 逐案判定表（`ekgLedger.mjs`）

使用者 2026-08-10 要求：**跑完就該留下每一件的歸屬，別人來問時不必重跑。**
在這之前三種紀錄沒有一種答得出「這一件算在哪」：

| 原本的紀錄 | 為什麼不夠 |
| --- | --- |
| `out/raw/{月份}-ekg-verify-progress.json` | 有全部結果，但**跑完就刪**（含完整 TEMSIS，屬個案明細） |
| `out/last-run.log` | **每次執行整份覆寫**，上個月的早就不在了 |
| 待人工確認清單 | **只收判不出來**的那幾件 |

因此改為每次跑完正式流程都寫出一份逐案判定表，涵蓋**分母（聯集）的全部案件**，
一件一列：`分隊｜案件日期｜TEMSIS｜勾EKG檢查｜有12導程｜到院時間｜上傳時間｜判定｜計入分子｜依據`。
**沒進分子的排前面**（來對數字的人要看的就是這些），同組內再依案件日期排。

判定欄一定分得出這三種，不可混為一談：

| 判定欄 | 意思 |
| --- | --- |
| `到院前` | 查核過，上傳早於到院 → **計入分子** |
| `到院後`／`無法判定` | 查核過但沒過 |
| **`沒有12導程，未查核`** | 分母裡有這件，但**根本沒有 12 導程可查**（只勾了 EKG檢查）。不是判成到院後 |
| `未查核` | 有 12 導程，但這次沒查到這一件（中途中止或 `--limit`） |

> ⚠ 這份落在 **`out/internal/`** 而不是 `out/report/`（使用者 2026-08-10 要求）：
> `out/report/` 裡的東西是會發給各分隊的，而這份含**全局每一件案子**的判定與依據，
> 不能給分隊看。放在一起遲早會整個資料夾一起寄出去。
>
> 有申訴時多一個 **`申訴處理`** 分頁（分隊｜表上填的案件日期｜TEMSIS｜處理結果｜配對方式｜說明）——
> 申訴改判過的那幾件，光看逐案判定表只會看到原始判定，看不出被改過。
> **發生地點不寫進去**，它只用來比對。
>
> ⚠ 這份表與正式報表**同進退**：`--limit`／`--squad`／`--no-verify` 這類查核不完整的跑法
> 一律不寫。否則整批案件會被標成「未查核」，擺在 `out/report/` 裡看起來像是真的沒查到，
> 比沒有這份檔案更糟。
>
> 個資：含完整 TEMSIS 與時間，比照另外兩份清冊——只落在 `out/report/`（已 gitignore、不上雲），
> 終端機與 log 仍一律只印末 4 碼。

後兩份是**附帶清單**，沒有對應案件時不但不產生，還會**把上一輪留下的舊檔刪掉**
——不刪的話，一份寫著「5 件判定不出來」的舊清單會一直躺著，看起來像是這次的結果。

「有處置未勾選」的成因見 3.13（ZOLL 監視器自動上傳，但不會自動勾急救處置）。
這份清冊在**主流程裡順便算出來**：兩份匯出檔本來就都在手上，取差集不必再查一次系統。
2026-08-05 之前檔名為「心電圖-有12導程沒勾EKG-…」，改名後**不代為刪除舊檔**
（那是使用者的檔案，可能已手動編輯過），只在紀錄裡提醒可自行刪除。

兩份清冊的欄位：

| 清冊 | 欄位 |
| --- | --- |
| 有處置未勾選（分頁一） | 分隊｜漏勾件數（第一列為合計，其餘依件數由多到少） |
| 有處置未勾選（分頁二） | 分隊｜案件日期｜**TEMSIS（完整）** |
| 待人工確認 | 分隊｜案件日期｜**TEMSIS（完整）**｜到院時間｜讀到的上傳時間｜判定｜說明 |

> ⚠ **兩份清冊的 TEMSIS 都完整顯示**（使用者 2026-08-06 決定）。
> 兩份的用途都是「拿著它回系統把案件叫出來」——一份給各分隊核對漏勾的處置，
> 一份給使用者自己判斷傳輸時間——遮成末 4 碼反而要先用日期與分隊查一輪再比對，
> 而看得到這些案件的人本來就看得到完整編號。
>
> 其餘防線不變：檔案落在 `out/report/`（已 gitignore、不上雲），
> **終端機畫面與 `last-run.log` 仍一律只印末 4 碼**（那些是會被截圖、被貼出來的地方）。

**版面規則（三份輸出共用，見 `sheetLayout.mjs`）：**

- 第 1、2 列（大標與欄名）一律**水平垂直置中**。
- 欄寬依「欄名 ＋ **所有資料列**」計算。只看欄名會出事：「案件日期」欄名只有 4 個字，
  值卻是 `2026/07/01 09:27:02`（19 個字元），照欄名給寬度就被截掉（2026-08-05 使用者回報）。
- 跨欄合併的大標另外保證放得下：**合併儲存格放不下不會溢出到隔壁，而是直接被切掉**，
  因此總寬不足時把差額補在最寬的那一欄。
- **大標的需求寬度要再乘 `REPORT_FORMAT.titleWidthFactor`（1.15）留餘裕**
  （2026-08-11 加）。沒有它每次都**剛好差一點點**而被切掉，原因有二、兩個都是低估：
  ① 大標一律是**粗體**，同樣的字比一般字寬約一成，字寬公式沒算進去；
  ② 補寬度時補到「理論值」為止，總寬永遠**等於**需求值，實際字型只要多佔半格就露出來。
  實測 `2026-07　有EKG處置無12導程清冊` 的理論需求與總寬同為 42，正好卡在邊界。
- 大標只寫用途（例如「2026-07　有處置未勾選清冊」），不寫成一長串條件說明。

### 3.8 個資保護（本流程特別注意）
| 規範 | 作法 |
| --- | --- |
| 進度檔含完整 TEMSIS | 只落在 `out/raw/`，與匯出明細**一起刪除**（`--keep-raw` 才保留） |
| 傳輸紀錄畫面 | `findMarkedRows` 是 `pageFinder.mjs` 唯一會帶出資料格內容的模式，防護放在限縮範圍：**只回傳命中「12導程」的那幾列**、每格截斷、5 碼以上數字遮蔽 |
| 下拉選單的內容不算資料 | 取列文字時會**移除 `<select>/<option>`**——查詢頁的心電圖下拉本身就有一個叫「12導程心電圖」的選項，不排除的話那一整列查詢條件會被當成一筆上傳紀錄（實測踩到） |
| 紀錄表全文 | 只在記憶體，取出到院時間與指派案號後即棄，不落檔、不截圖 |
| 畫面與 log | TEMSIS 一律 `maskCode` 只顯示末 4 碼（**兩份清冊的 Excel 除外**，見 3.7） |

### 3.14 分隊申訴表（`ekgAppeal.mjs`）

同仁可能因為**種種非個人因素**沒能順利上傳、或變成到院後才上傳。
只要把案件填進申訴表，那一件就算成「有在到院前傳」（使用者 2026-08-10 定的規則）。

資料來源是**到院前預警那份 Google 試算表的第二個分頁**，
網址（含 `#gid=`）放在 `tools/ems-report/.env` 的 `EMS_EKG_ADJUST_SHEET_URL`。
gid 由程式自己從網址抓，不必另設變數；**沒設定就整段略過**，不影響報表產出。

#### 處理規則

1. **第一列資料是範例，固定跳過**（`EKG.appeal.exampleRowCount`）。跳過時會在畫面上明講——
   哪天有人把範例刪掉，默默少算一件是沒人會發現的錯。
2. 只處理**案件日期落在查詢期間內**的列（那張表是累積的，橫跨好幾個月）。
3. 找出它對應到系統裡哪一件：

| 順序 | 比對條件 | 用在什麼時候 |
| --- | --- | --- |
| 1 | **TEMSIS**（22 碼） | 正常情形 |
| 2 | **分隊＋發生地點＋時間相差 10 分鐘內** | TEMSIS 長度不對或查不到時 |

> 後備比對三個條件**要同時成立**：只比時間會配對到同分隊同時段的別件；
> 只比地點則同一個養護機構一個月可能出勤很多次。
> **配對到兩件以上時不選**，回報讓人自己看——選錯會把調整加到別人的案件上。
> 容差 10 分鐘是使用者 2026-08-10 指定（原提案 30 分鐘，放寬反而容易配錯）。

4. 依比對結果調整：

| 比對結果 | 分母 | 分子 | 有處置未勾選清冊 |
| --- | --- | --- | --- |
| 找得到，**且已計入分子** | 不變 | **不變** | 不變 |
| 找得到，未計入分子（到院後／判不出來／沒有 12 導程） | 不變 | **+1** | 不變 |
| 找不到（**不在本次兩份查詢結果裡**：既沒勾處置也沒上傳） | **+1** | **+1** | **+1** |
| TEMSIS 長度不對**且**後備比對也配不到 | 不變 | 不變 | 不變（列為「無法處理」） |

> ⚠ **已計入分子的不可以重複加**，否則分子會超過分母——那是數學上不可能的數字，
> 整份報表就不可信了。
>
> ⚠ **TEMSIS 長度不對時絕不可以當成「系統查無此案」**。實測 30 筆裡有 4 筆是 17 碼，
> 當成查無此案會讓分母分子平白各加 4 件，但它們多半只是打錯或少貼。

#### 人手填的時間寫法

實測（2026-08-10）30 列裡有 **5 列**因為寫法特別而被丟掉，其中一列還在查詢月份內
——**申訴被默默漏掉，分隊卻以為填了就會算**。因此 `normalizeSheetDateTime()` 先做正規化：

| 表上的寫法 | 轉成 |
| --- | --- |
| `2026/07/08 0620` | `2026/07/08 06:20`（時間寫成 4 碼、沒有冒號） |
| `2026/6/6 上午 7:03:00` | `2026/6/6 07:03:00`（中文半日制；下午加 12、正午與午夜特別處理） |
| `2026/07/19`（只有日期） | 當天 00:00，並記下 `hasTime: false` |

> 只填日期時**後備比對改成比「同一天」**。仍照 10 分鐘容差比的話，
> 會拿當天 00:00 去比，等於後備路線直接斷掉。有 TEMSIS 的照樣直接比對，不受影響。

> 刻意不改 `timeParse.mjs`：那支是讀**系統畫面**的，格式由系統決定、相對規矩；
> 這裡才是人工填寫的表單，兩者該分開放寬。
>
> 仍然解析不出來的列會**列出試算表列號**請人回去修，不會只說「有幾列有問題」。

#### 為什麼要在逐案查核**之後**才做

要先知道每一件算不算進分子，才判斷得出這筆申訴是「本來就算進去了」還是「要補」。
因此 `--limit`／`--squad`／`--no-verify` 這類**查核不完整的跑法一律不套用申訴**——
那時多數案件還沒有查核結果，會把「還沒查」誤當成「查了沒過」而全部補進分子，
數字會憑空變好看。

#### 個資

這張表另有「患者姓名」「送往醫院」等欄位。程式**只讀 TEMSIS ID／案件日期／救護車編號／發生地點**四欄，
其中**發生地點只在記憶體裡做比對，不寫進任何輸出檔、不印在畫面上**。
畫面與紀錄檔上的 TEMSIS 一律只顯示末 4 碼。

分隊由**救護車編號**推出（`平鎮91` → `平鎮分隊`）——那張表沒有分隊欄。
推不出來的（例如範例列的 `xx91`）**不猜**，列出試算表列號請人補。

### 3.15 產出檔的保留期限（`retention.mjs`）

使用者 2026-08-10 要求「月報至少存三個月，超過就可以刪」。
`run`／`ekg`／`monthly` 跑完後會掃 `out/report/` 與 `out/internal/`，
只留最近 `REPORT_RETENTION_MONTHS`（預設 3）個月份。

| 規則 | 理由 |
| --- | --- |
| 保留範圍依**檔名裡最新的月份**往回算，不是依今天 | 補跑舊月份（`--month=2026-05`）時，不該把比它新的檔案掃掉 |
| **只刪檔名結尾是 `-YYYY-MM` 的產出檔** | 使用者自己放進去的檔案認不出月份，一個都不會被碰到 |
| 刪不掉只警告、不中斷 | 多半是被 Excel 開著，而報表這時都已經產好了 |
| 同一個月份的檔案一起留或一起刪 | 只刪一半會留下對不起來的半套資料 |

### 3.12 診斷指令 `ekg-diag`

`捷徑/不常用/心電圖-查條件與畫面.bat`，**只查不算、不產生任何報表**。
存在的理由：伺服器端登入很快就逾時，每問一件事就要重打一次驗證碼，
因此把「要當面問系統的問題」集中在一次登入裡問完：

1. 量 A／B／C 三種條件的件數（含聯集與交集）
2. 拿一筆真案件，把「傳輸紀錄」與「上傳」兩個畫面的表格欄位與內容列出來對照
3. 量「加上已結案＋送醫」會差多少
4. 挑出「有 12 導程卻沒勾 EKG檢查」的案件，依救護狀態／送醫情形交叉分析
   （**用不限狀態的 A／B**：資料先篩成「已結案＋送醫」的話，這兩個面向每一件都長一樣，分析不出東西）
5. 把**分母的兩塊差集**各自列成清冊（**用 A2／B2**，與正式報表同口徑）

#### 分隊說「我自己查比較少」怎麼回答（第 5 項的用途）

分母是**聯集**，所以它比任何單一條件都多，可以拆成三塊：

```
分母 ＝ 兩者都有 ＋ 只有 12 導程 ＋ 只勾 EKG檢查
```

分隊只用其中一個條件自己查，件數當然對不上，差的就是另外那一塊。
第 5 項把兩塊各寫成一份清冊，逐案清單裡有 TEMSIS，可以直接指出「多的是哪一件」：

| 檔案 | 內容 | 誰會少算 |
|---|---|---|
| `out/report/心電圖-有處置未勾選清冊-{YYYY-MM}.xlsx` | 有 12 導程、沒勾 EKG檢查 | 只勾「EKG檢查」查的人 |
| `out/report/心電圖-有EKG處置無12導程清冊-{YYYY-MM}.xlsx` | 勾了 EKG檢查、沒有 12 導程 | 只選「心電圖＝12導程」查的人 |

> ⚠ 這一段**必須用 A2／B2**（已結案＋送醫）。用不限狀態的 A／B 會產出跟正式報表
> 對不起來的清冊，而且「有處置未勾選清冊」與正式流程**檔名相同**，會把正式那份蓋掉。

**同樣的條件只跑一次**：一次查詢＋匯出約一分鐘，重複問等於平白讓人多等
（原本要 9 次，合併後 5 次）。另會存出 `out/probe/匯出檔欄名.txt`——
匯出檔有 243 欄、欄名與畫面標籤未必相同，沒有這份清單就只能再登入重跑一次
（**只有欄名，不含資料**）。

個資保護：匯出檔只用來數筆數，數完立刻刪；畫面上的列**只印時間與檔案類型欄**，
不印上傳者姓名；TEMSIS 一律只顯示末 4 碼。

### 3.12.1 OHCA 對撞診斷 `ekg-ohca`

```
node tools/ems-report/index.mjs ekg-ohca --month=2026-07 [--temsis=A,B,...]
```

**只查不算，不動任何正式報表。** 2026-08-12 新增。

#### 為什麼要有這一支

使用者發現三民 7/12 那件「其實是 OHCA 心電圖，不是 12 導程」。查證結果
**查詢條件沒有抓錯**——心電圖下拉 `#_selEKG` 本來就把三種分成不同選項：

| 選項 | value |
|---|---|
| 全部心電圖 | （不限） |
| **12導程心電圖** | **1** ← 正式報表用的 |
| 到院前OHCA心電圖 | 2 |
| 到院後OHCA心電圖 | 3 |

（value 由 2026-08-12 實跑確認；程式仍以**選項文字**反推，不寫死這些數字。）

執行紀錄留著 `心電圖＝12導程心電圖（已確認）`，套用後有回讀驗證。
也就是說，那件在**系統資料裡**就掛在 12 導程底下，問題出在來源資料而非本工具。

因此要回答的問題變成「這種誤標到底有多少件」。

#### 判定規則：**處置勾了 CPR ＝ OHCA 案件**（使用者 2026-08-12 提供）

這是這支診斷的核心。CPR 與 EKG檢查同在「急救處置進階搜尋」區塊，是個**勾選框**，
所以一次查詢就撈得出整批，不必逐案開救護紀錄表（284 件要跑一兩個小時）。

2026-07 實跑結果：**12導程 ＋ 處置勾CPR ＝ 4 件**（占 284 件的 1.4%）

| 分隊 | 案件日期 | 目前判定 | 計入分子 |
|---|---|---|---|
| 龜山分隊 | 07/10 21:47:22 | 到院前 | **是** |
| 三民分隊 | 07/12 15:38:39 | 無法判定 | 否 |
| 平鎮分隊 | 07/19 12:13:17 | 到院後 | 否 |
| 大有分隊 | 07/23 18:06:19 | 到院後 | 否 |

使用者原本回報的三民那件正在其中，規則對得上。

> ⚠ **CPR 條件必須每一次查詢都明講勾或不勾**。這系統的查詢條件會殘留，
> 只在要勾的那一次傳的話，後面每次查詢都被偷偷多加一個條件，件數全部是錯的。
> `queryAndExport` 的 `extraCheckboxes` 就是為此而設。

#### 兩條路互相印證

**一、條件對撞**：用 OHCA 兩個選項各查一次（條件與正式報表同口徑：已結案＋送醫，
且**一律不勾 EKG檢查**，免得混進「有沒有勾處置」這個變數），再比對 TEMSIS。
有案件同時出現在 12 導程那份裡 → 同一件被掛了兩種心電圖，那是分母被灌水的直接證據。

> ⚠ 三個選項**必須來自同一個下拉**，程式會檢查；不同就中止。
> 不同代表畫面上不只一個心電圖欄位，那三次查詢就不是同一個維度的比較。

實跑結果：**三種類型在系統裡是互斥的**（12導程 284、到院前OHCA 18、到院後OHCA 18，
與 12 導程的重疊都是 0）。所以誤標**不會從類型對撞看出來**——只有從處置才看得出來，
這正是 CPR 規則的價值所在。

> 兩個 OHCA 選項彼此重疊 17 件（各 18 件）——同一件可能同時有到院前與到院後的
> OHCA 心電圖，屬正常。程式會檢查「兩邊是不是完全同一批」，
> 若完全相同代表下拉根本沒切換成功，會警告結論不可信。

**二、看救護紀錄表**：`--temsis=` 指定的案件會抓紀錄表，讀 OHCA 判斷欄位的**值**。

> ⚠ **數字樣次數是沒有用的，這點已被實跑推翻。** 紀錄表是表單，欄位標籤每張都印著：
> 三民那件（實際 OHCA）與同分隊對照案件的字樣次數幾乎一模一樣——
> 電擊 4:4、CPR 3:3、心肺功能停止 3:3、去顫 1:1，只有 OHCA 差 2:1。
> `EKG.ohca.sheetMarkers` 因此**只留著當對照**（值都一樣就證明那些字是印好的標籤），
> **不可以拿來當判定依據**。
>
> 改讀欄位值之後也只有 `檢傷分級` 有差（第1級 vs 第3級），仍不足以單獨判定。
> **真正可靠的是處置勾選的 CPR。**

> ⚠ 紀錄表 PDF 取出來的文字**沒有欄位邊界**，一個值會一路吃到下一個標籤
> （`旁觀者CPR：有 使用PAD：無 ROSC：08:12` 會整串當成旁觀者CPR 的值）。
> `readOhcaFields` 會切在下一個 `標籤：` 之前，否則兩件比對永遠看不出差別，
> 還會把沒要讀的欄位一起帶出來。

#### 產出

`out/internal/心電圖類型對撞-{YYYY-MM}.xlsx`，三個分頁：各類型件數｜同時掛兩種類型｜救護紀錄表字樣。
含完整 TEMSIS，**內部診斷紀錄，不要發給分隊**。

#### 個資保護（比 `ekg-diag` 更嚴）

| 資料 | 處理 |
| --- | --- |
| 匯出檔 | 只用來數筆數與比對 TEMSIS，讀進記憶體後**立刻刪檔** |
| 紀錄表全文 | **只在記憶體裡數次數**，不落檔、不印內容 |

| TEMSIS | 終端機一律只印末 4 碼 |

## 5. 線上解鎖工單（v1.17 起）

各分隊在網頁上提出解鎖申請，救護科的電腦統一處理，結果自動回到網頁。

### 5.1 為什麼實際解鎖不能在網頁做

這一節是整章的前提，先講清楚免得日後又被問一次：

| 原因 | 說明 |
| --- | --- |
| **驗證碼** | 目標系統每次登入都要驗證碼，而本工具的鐵則是由使用者本人辨識、不自動破解（0.3） |
| **瀏覽器擋住** | 網頁跑在 `ems-system-su1220.web.app`，跨網域操作 `emsdt.tyfd.gov.tw` 會被 CORS 擋死，且那是全靠 POST 導頁的 frameset 老系統 |
| **搬上雲要存帳密** | 用 Cloud Functions 開無頭瀏覽器的話，救護系統的帳密就得放到雲端，違反「帳密只從本機 `.env` 讀」 |

**因此雲端只當「信箱」**：網頁負責申請與查結果，實際連線與解鎖永遠是救護科那台電腦。

### 5.2 流程

```
網頁（任何裝置）            Firestore（信箱）            救護科電腦（手動執行）
 貼上 TEMSIS ＋ 事由  ──▶  unlockRequests 建立    ──▶  雙擊「線上解鎖工單.bat」
                            status: pending             先拿工單（沒有就不開瀏覽器）
                                                        登入救護系統（本人打驗證碼）
 逐筆亮起結果        ◀──  status/result 回寫     ◀──  每解完一筆立刻回寫一筆
```

**先拿工單、再開瀏覽器**：沒有待處理工單時就不必白登入一次救護系統。

**逐筆回寫，不等整批跑完**：中途關掉視窗時，前面做完的幾筆在網頁上才不會停在「待處理」。
回寫失敗只警告不中斷——案件已經解了，雲端寫不寫得進去是另一回事
（那一筆會停在「處理中」，紀錄檔會明講）。

### 5.3 兩種執行方式：一次性 vs 常駐監看

| | 一次性 `unlock-online` | 常駐監看 `unlock-watch`（v1.18 起） |
| --- | --- | --- |
| 行為 | 抓當下所有待處理工單，處理完就結束 | 一直開著，有新工單就處理 |
| 驗證碼 | 每次執行打一次 | **只在開始時打一次**，之後靠心跳維持 |
| 反應時間 | 你什麼時候跑就什麼時候處理 | 最慢 `pollMs`（預設 20 秒） |
| 適合 | 一天處理一兩次 | 電腦本來就整天開著 |

**常駐監看為什麼可行**：關鍵是**不讓登入過期**。伺服器端是閒置逾時
（使用者 2026-08-06 判斷），因此每 5 分鐘做一次無害的切頁（切到救護紀錄表查詢頁）
就能續命。這**不是繞過驗證碼**——驗證碼仍由本人輸入過一次，之後只是不讓那次登入過期，
等同自己開著分頁不關。

**這個設計不賭那個前提**：萬一系統其實有絕對上限，心跳擋不住，掉線時會照樣停下來
請本人重新登入（`ensureSignedIn`，在同一個瀏覽器視窗，不必整個重開），程式不會壞掉，
只是要多打幾次驗證碼。

**試跑模式本身就是量測工具**：`unlock-watch`（不加 `--execute`）會登入、心跳、監看，
但不解鎖也不回寫。放著跑就能看出登入到底能撐多久。

#### 掉線時絕不可以把案件寫成失敗

處理到一半被踢掉的話，後面每一筆都會得到「查無案件」——但那是因為根本沒登入，
不是案件真的有問題。照實寫回去的話，申請人看到的是「需人工處理」，
**而實際上什麼事都沒發生，那是在騙人**。

因此 `processBatch` 在每一筆看起來失敗時多做一次 `isSignedIn` 檢查：
沒登入就把工單**退回 `pending`**（`resetToPending`），下一輪重新登入後自動再跑一次。
成功的案件不做這個檢查，不浪費時間。

#### 節奏設定（`UNLOCK.watch`）

| 設定 | 預設 | 說明 |
| --- | --- | --- |
| `pollMs` | 20 秒 | 多久問一次雲端有沒有新工單（只碰 Firestore，很輕） |
| `heartbeatMs` | 5 分鐘 | 多久戳一次救護系統維持登入。遠短於一般閒置上限（20~30 分），又不會頻繁到像在洗頁面 |
| `statusEveryMs` | 30 分鐘 | 沒事時多久報一次「還活著」（順便顯示已連續登入多久） |

**為什麼用輪詢而不是即時監聽（onSnapshot）**：我們自己回寫狀態也會觸發監聽，
處理到一半又被自己的寫入叫醒，要處理重入問題。輪詢單純得多，
而 20 秒的延遲對「等人來解鎖」這件事完全無感。

#### 掉線之後：**一直等，絕不自己結束**

2026-08-06 首次整夜實跑踩到的問題：凌晨 06:53 掉線時使用者在睡覺，
舊版沿用一次性流程的「10 分鐘沒登入就放棄」，逾時後整個程式退出——
早上看到的是一個**已經死掉的視窗**，而那之後完全沒有在監看。

現在的行為：

| | 舊版 | 現在 |
| --- | --- | --- |
| 掉線後 | 等 10 分鐘 | 每 `reloginWaitMs`（5 分鐘）重試一次，**無限期** |
| 等不到 | **整個程式結束** | 記下狀態、跑下一輪再等 |
| 提醒 | 只講一次 | 每 30 分鐘再提醒一次，並在終端機**響一聲** |
| 這期間 | — | 不做任何解鎖動作；新工單留在「待處理」，登入後一起處理 |

每一輪重試都會重新導向登入頁並代填帳密，所以使用者走回電腦前看到的
一定是「可以直接打驗證碼」的狀態，不會是一個過期的畫面。

「已連續登入多久」從**最近一次登入**起算（`signedInSince`），不是從程式啟動起算——
掉線重登之後那個數字要歸零，否則量不出真正的 session 壽命。

### 5.4 實跑結果（2026-08-06 整夜，試跑模式）

| 項目 | 結果 |
| --- | --- |
| 登入時間 | 00:06（本地） |
| 心跳 | 每 5 分鐘一次，**81 次全部成功** |
| 連續登入 | **6 小時 46 分** |
| 掉線時間 | 06:53 |
| 掉線徵狀 | 心跳切頁時 `找不到名為 contentSidemenu 的 frame`（被踢回登入頁，frameset 沒了） |

**結論：心跳確實有效，該系統的確是閒置逾時。** 撐了將近 7 小時，中間完全沒掉線。

06:53 這個時間點很可能是**系統每日重啟或絕對逾時上限**，一次資料還判定不了。
再跑幾天若都落在同一個時間點，就是排程性的，可以預期。

#### 紀錄一定要邊跑邊落檔

`last-run.log` 是**程式結束時**整份覆寫的。對跑一整天的監看而言等於沒有紀錄：
程式還活著就什麼都查不到，而它被結束的方式多半是「直接關掉視窗」——那時也來不及寫。

2026-08-08 就因此吃了虧：監看中途掉過線，程式正確地留在「等待登入」狀態沒有結束，
但**完全查不出是什麼時候掉的、掉線前最後一次心跳是幾點**。

因此監看另外寫一份 `out/watch.log`：

| | `last-run.log` | `watch.log` |
| --- | --- | --- |
| 寫入時機 | 程式結束時 | **每一行即時追加** |
| 跨執行 | 整份覆寫 | **追加**，每次執行加一條分隔線 |
| 用途 | 一次性指令的完整紀錄 | 監看的歷史（查「前天半夜發生什麼事」） |

落檔失敗一律安靜吞掉——紀錄寫不進去（磁碟滿了、檔案被鎖）不該影響正在進行的解鎖。

⚠ 寫入刻意用**同步**的 `appendFileSync`。監看最常見的結束方式是「直接關掉視窗」，
那在 Windows 上是把程序硬砍：非同步的寫入還排在佇列裡就會一起消失，
而那幾行往往正是掉線當下最關鍵的訊息（2026-08-08 實際損失過一次）。
這個檔案一小時只寫幾行，同步寫入的代價可以忽略。

#### 一直開著的兩個代價（使用者自行衡量）

1. **辦公室電腦會整天掛著一個已登入的公務系統**。任何人走過去就是已登入狀態——
   這是單位的政策問題，不是技術問題。
2. 電腦關機或睡眠就沒人處理了，工單會排在佇列裡等下次開起來。

### 5.5 資料模型 `unlockRequests/{id}`

**一個 TEMSIS 一張工單**（不是一張工單包一串），這樣每一筆的狀態與結果各自獨立，
網頁上也能逐筆亮起來。欄位定義在 `src/types/unlockRequest.ts`，兩端共用。

| 欄位 | 內容 |
| --- | --- |
| `temsis` | 要解鎖的編號（**完整**，本機要拿它回系統查） |
| `reason` | 申請事由 |
| `requestedBy` / `requestedByName` | 申請人 uid 與顯示名稱（存名稱是為了看清單時不必再查 users） |
| `requestedAt` | 申請時間 |
| `status` | `pending` → `running` → `unlocked`／`noAction`／`failed` |
| `result` | 案件日期、出勤車輛、分隊、說明、處理時間、執行者 |

狀態對照（`unlockQueue.toQueueStatus`，有測試釘住）：

| 本機 `UnlockOutcome.status` | 工單狀態 | 網頁顯示 |
| --- | --- | --- |
| `已解鎖` | `unlocked` | 已解鎖 |
| `無需處理` | `noAction` | 案件未結案 |
| `需人工處理`／`查無案件`／`失敗` | `failed` | 需人工處理 |

沒見過的狀態一律當 `failed`——寧可讓人多看一眼，也不要誤報成已解鎖。

> **`result.detail` 照樣寫完整的，但網頁只給管理員看**（v1.18.3 起，使用者 2026-08-09 指定）。
> 申請人看到的是一句白話（「已解鎖，可以進系統修改了」之類，對照表在網頁端的
> `UNLOCK_RESULT_SUMMARY`）——`detail` 寫的是第幾張紀錄表、比對到哪個按鈕、
> 畫面出現什麼訊息，那是給維護的人看的。**本機這一端不要為此縮減內容**：
> 真正要追過程時看的是 `out/watch.log`，寫得越清楚越好。
>
> 管理員另外可以對任何一張工單「重新送單」（退回 `pending` 並清空 `result`）或「刪除」。
> 重新送單之後，常駐監看下一輪就會把它撿起來重跑，本機端不必做任何調整。

### 5.6 本機端怎麼連上雲端

**不用服務帳號金鑰**（`docs/TODO.md` 原本的規劃），改用**一般帳號登入**：

| 設定 | 從哪來 | 為什麼 |
| --- | --- | --- |
| Firebase 專案設定 | 專案根目錄 `.env` 的 `VITE_FIREBASE_*` | 這些值本來就會被打包進公開的網頁檔案，不是機密，共用同一份免得兩邊不同步 |
| 登入帳密 | `tools/ems-report/.env` 的 `EMS_WEB_EMAIL`／`EMS_WEB_PASSWORD` | 已 gitignore，比照救護系統帳密的既有作法 |

服務帳號金鑰等於一把繞過所有安全規則的萬能鑰匙，放在辦公室電腦上風險太高；
用一般帳號登入的話，這支程式**受和網頁完全相同的規則約束**——
規則測試涵蓋到的行為就是它實際能做的事。

帳號必須是**一般使用者或管理員**：解鎖專用帳號依規則沒有回寫結果的權限。

#### 用 Google 登入的人要多做一步（2026-08-06 實際卡到）

使用者平常是用 Google 登入，而 **Google 登入沒有密碼可以填在 `.env`**
（那組密碼是 Google 的，本系統拿不到也不該拿）。因此第一次設定必然卡在這裡。
作法是另開一組**專門給程式用**的帳號：

1. 開 `https://ems-system-su1220.web.app/register`（建立新帳號那一頁，不要按 Google 登入）
2. 填一組只給程式用的帳密。Email 建議用 Gmail 的 `+` 別名
   （例如 `你的帳號+unlock@gmail.com`）——信一樣進原本的信箱，
   而且**不會**命中管理員白名單（白名單是完整字串比對），因此會是一般使用者
3. 用平常的 Google 帳號登入 → 使用者管理 → **核准**它，角色維持「一般使用者」
4. 把帳密填進 `tools/ems-report/.env`

**為什麼另開一組而不是用自己的**：`.env` 放在辦公室電腦上，萬一外流，
被拿走的只是一個一般使用者帳號（不能刪業務、不能管帳號），且隨時可在使用者管理停用。

> Firebase 專案的「電子郵件/密碼」登入方式**已確認為啟用**（2026-08-06 以 REST API 探測，
> 回 `INVALID_LOGIN_CREDENTIALS` 而非 `OPERATION_NOT_ALLOWED`）。若日後被關掉，
> 程式會回報 `auth/operation-not-allowed` 並指出要去主控台哪裡開。

所有與這組帳密有關的錯誤都會附上上面四步，不會只丟一句「登入失敗」。
登入成功卻讀不到工單時另有專屬訊息，指向兩個真正的原因：**帳號還沒核准**、
**角色被設成解鎖專用**。

### 5.7 指令與捷徑

| 捷徑 | 指令 | 行為 |
| --- | --- | --- |
| `捷徑\線上解鎖工單.bat` | `unlock-online --execute` | 一次性：處理當下所有工單後結束 |
| `捷徑\線上解鎖工單-自動監看.bat` | `unlock-watch --execute` | **常駐**：一直開著，有新工單就處理 |
| `捷徑\不常用\線上解鎖工單-試跑.bat` | `unlock-online` | 只列出有哪些待處理工單，不解鎖、不回寫、不開瀏覽器 |
| `捷徑\不常用\線上解鎖工單-監看試跑.bat` | `unlock-watch` | 登入並維持登入但不解鎖——**用來量登入能撐多久** |

與 `unlock` 同一套安全預設：**沒加 `--execute` 就是試跑**。
中間實際解鎖的那一段是同一支 `runUnlockFlow`，沒有另一套邏輯——
差別只在「TEMSIS 從哪來、結果往哪去」。

### 5.8 用完一定要關連線

**Firebase 的連線會撐著 Node 的事件迴圈。** 不呼叫 `closeQueue()` 的話，
事情都做完了、訊息也印完了，黑色視窗卻一直不會結束——看起來就像當掉
（2026-08-06 實測踩到：試跑明明 0.8 秒就讀完工單，指令卻永遠不結束）。

因此 `runUnlockOnlineCommand` 把實際內容包在 `try`／`finally` 裡，
不論成功、失敗或中途拋錯都會 `terminate(db)` ＋ `deleteApp(app)`。
**登入失敗那條路也要關**——app 在 `signInWithEmailAndPassword` 之前就建立了。

關不掉只警告不拋錯：事情已經做完了，不該因為收尾失敗就讓整個指令算失敗。

## 6. 開通大量傷患系統權限（v1.22 起）

`tools/mci-perm/`。把「幫一個人開通 MCI 大量傷病患救護管理系統權限」做成程式：
登入一次，整份名單一路做完，最後給一份「誰成功、誰要自己補做」的清單。

> 本章的每個「⚠」幾乎都是 **2026-08-18 首次實跑**換來的，不是預想出來的。
> 那天連跑六輪才把流程走通，過程記在 6.13。

### 6.1 這是「另一個系統」

**與第 1～5 章的緊急救護管理系統（`emsdt.tyfd.gov.tw`）完全無關**。
目標是消防署的**緊急醫療救護智能平臺「救急救難一站通」**（`/SSO/`），
底下掛著十幾個子系統（ATM、DQC、ADG、AAM、CPM、DSM、FOS、MMS、**MCI**、ACS、FIS、PAC、EWFA）。

這是本專案第一個連向第二個外部系統的工具，因此刻意做成**獨立目錄、獨立設定**：

| 項目 | 救護紀錄表工具 | 本工具 |
| --- | --- | --- |
| 位置 | `tools/ems-report/` | `tools/mci-perm/` |
| 網址 | 寫在 `config.mjs` | 寫在 `.env` 的 `MCI_ENTRY_URL` |
| 帳密 | `.env` 的 `EMS_USERNAME`／`EMS_PASSWORD` | `.env` 的 `MCI_USERNAME`／`MCI_PASSWORD` |
| 登入狀態 | `tools/ems-report/.auth/state.json` | `tools/mci-perm/.auth/profile/`（整個瀏覽器資料夾） |
| npm 指令 | `npm run tool:ems` | `npm run tool:mci` |

**兩邊不共用任何程式碼**（`logger.mjs`、`xlsxNode.mjs` 是各自一份的副本）。
理由：一個工具要能單獨打包成可攜版，跨目錄 `import` 會讓打包後的相對路徑失效。

> ⚠ 設定填錯地方會完全跑不動：使用者第一次把 `MCI_*` 三行填進了
> `tools/ems-report/.env`，本工具只讀自己目錄的 `.env`，於是回報「還沒設定網址」。

### 6.2 流程（就是使用者原本的六個步驟）

| 步驟 | 動作 | 程式怎麼做 |
| --- | --- | --- |
| 0 | 登入 | 代填帳密、**自動選縣市別「桃園市」**、驗證碼由本人輸入 |
| 1 | 點右上角「OOO，你好」 | 找含「你好／您好」的可點元素（實際顯示為「蔡O佑，您好」） |
| 2 | 選「帳號子系統權限」 | 到站判定＝**姓名欄或搜尋鈕出現**（見 6.5） |
| 3 | 選單位、填姓名、**帳號關鍵字清成空白**、按搜尋 | 用 id 定位（見 6.4）；單位清單要等載入（見 6.6） |
| 4 | 確認查到的是一個人 | **讀系統寫的「共 N 項」**，不是數按鈕（見 6.7） |
| 5 | 按該列的「設定」 | 完全相符比對「設定」 |
| 6 | 選「MCI002 縣市端使用者」→ 按確定 | 用 `#MCIselect`＋`#MCI`（見 6.4） |

處理下一位時**不從步驟 1 重來**：做完一位還停在查詢頁，直接改條件重新搜尋即可（見 6.8）。

### 6.3 標籤判讀要認得七種版面寫法

`domFind.mjs` 的所有查找都在瀏覽器端由一個 `queryPage(params)` 做完
（送進 `frame.evaluate`，**因此不能引用模組外的變數**）。

⚠ 這個系統**不是**老式表格排版。第一次實跑時，查詢頁三個欄位全部被判成
「沒有標籤」，流程直接卡死。因此 `nearbyTextOf()` 依序試七種寫法：
`label[for]` → 包住的 `<label>` → 同列前一格（老式表格）→ 同一格內的文字 →
前面的兄弟節點 → **同一個容器裡的 label** → **往上三層容器的前一個容器**。
再認不出來，還會拿 `placeholder`／`title`／`aria-label` 與 `id`／`name` 來比對。

兩個一定要做對、已有測試守住的細節：

- **「帳號關鍵字」不可以誤中「帳號」**：一律**先找完全相同的標籤、再找包含**。
  誤中的後果不是報錯，而是姓名填進錯的欄位、帳號關鍵字沒清乾淨 → 永遠查不到人。
- **文字比對忽略所有空白**：`MCI002 縣市端使用者` 與 `MCI002縣市端使用者` 視為同一個。

排查用的列表會**遮蔽 5 碼以上連續數字**，避免帳號、身分證夾在文字裡被寫進紀錄。

### 6.4 有兩個地方一定要用 id

一般原則是「用畫面文字定位」，但這一頁有兩處非用 id 不可：

**查詢區**（`#searchDeptNotNfa`／`#searchNameNotNfa`／`#searchAccountNotNfa`）
這一頁**同時藏著「新增使用者」與「編輯使用者」兩整組表單**（`_txt*`、`edit_*`），
欄位標籤一模一樣（姓名、帳號、e-mail…）。靠標籤去猜很容易挑到隱藏的那一組。

**權限區**（`#MCIselect` 角色下拉、`#MCI` 勾選框）
⚠ **這一頁的子系統名稱與角色下拉在版面上是錯開的**：探測回報
`#ACSselect` 旁邊寫的是「MCI 大量傷病患救護管理系統」、`#DQCselect` 旁邊寫的是
「ATM 救護技術員管理系統」。用文字定位會設到**隔壁那個子系統**去——
那是這個工具唯一「會真的出事」的錯誤，因此權限區只認 id：
子系統代碼是什麼，id 就是什麼。

`#MCIselect` 的選項（實跑取得）：`請選擇權限`／`MCI001 署端使用者`／`MCI002 縣市端使用者`。

選完角色後會確認 `#MCI` 勾選框是勾起來的，**但只在沒勾的時候才勾**——
有些頁面選了角色會自動打勾，再點一次等於取消，那會變成「選了角色卻沒開通」。

### 6.5 到站判定不能只認一種東西

點完「帳號子系統權限」後，等的是**姓名欄位或搜尋按鈕，有一個出現就算到站**。
只認姓名欄的話，欄位標籤認不出來時會卡死在這裡，即使畫面其實早就到了。
等待上限 25 秒（原本 4 秒不夠，政府系統換頁本來就慢）。

### 6.6 單位清單是進頁面後才載入的

`#searchDeptNotNfa` 剛到站時是 **0 個選項**，載完有 **76 個**（消防局各科室＋各大隊分隊，
寫法與救護系統一致：「桃園分隊」「中壢分隊」…）。

不等就選，結果會是「沒有相符的選項」——看起來像單位打錯，其實只是還沒載入。
因此選單位前先等到選項數 > 1；探測也一樣要等，否則記錄下來的是一個空下拉。

### 6.7 人數要讀系統寫的數字

查詢結果的筆數改讀畫面上的「顯示第 1 至 10 項結果，**共 N 項**」（DataTables 樣式）。

⚠ 不能數畫面上有幾個「設定」按鈕：**一頁只顯示 10 筆**，查到 26 個人也只看得到
10 個按鈕，就會誤判成 10。而「查到幾個人」正是決定「要不要動手」的關鍵判斷。
讀不到筆數文字（系統改版）時才退回數按鈕，並在紀錄裡寫明是用哪種方式數的。

數之前要先等畫面上的「載入中」消失，否則讀到的是上一次查詢的結果。

### 6.8 三個「不能做」的動作

這三件事都是實跑時親手把流程弄壞才確認的：

| 不能做 | 會發生什麼 |
| --- | --- |
| **用網址直接開查詢頁**（`/SSO/subSystemSetForm`） | GET 只會得到一個空白頁（畫面上只有一個時間戳），而且導航過去後連主畫面都回不去 |
| **用 `goto` 回登入網址來「回主畫面」** | 這個系統的主畫面是登入後**動態切換**出來的，重新 GET 一律退回登入表單——等於把自己登出 |
| **每處理完一位就從步驟 1 重來** | 查詢頁上**沒有**右上角的「你好」選單（可點的只有回到選擇系統／登出／搜尋／顯示全部／匯出Excel），第二位就會卡死 |

正確的回法：已在查詢頁就直接改條件；不在查詢頁也沒有「你好」時，
點查詢頁上的「**回到選擇系統**」回主畫面，再走一次選單。

### 6.9 看不懂就停手

這個工具會改別人的權限，因此每個「不確定」都是停手而不是猜：

| 情況 | 做法 |
| --- | --- |
| 查詢結果 0 筆 | 記為「查無此人」，往下一位 |
| 查詢結果 2 筆以上 | 記為「查到不只一人」，**不點任何一個**（實跑驗證過：緊急救護科查「蔡」得 4 筆，程式如實停手） |
| 單位同時符合兩個以上的下拉選項 | 不選，把候選印出來 |
| 單位打錯、選項裡沒有 | 不選，印出前 30 個候選讓使用者照抄 |
| 任一步驟找不到東西 | 記下**卡在哪一步**與**當時畫面上看得到什麼**，往下一位 |

> ⚠ 姓名欄是**關鍵字**比對（placeholder 就寫「請輸入姓名關鍵字」），
> 因此名單請寫**完整姓名**；只寫一個字通常會命中好幾個人而被跳過。

### 6.10 預設試跑，`--execute` 才真的動手

沿用第 2 章解鎖的慣例：預設走完六步但**不按「確定」**（角色選了不送出，系統不會有變化）。
`--execute` 會在開瀏覽器**之前**先問一次 yes/no，並印出「即將對 N 位設定 MCI002」
——名單貼錯（例如貼到別的單位）在這裡還救得回來。

### 6.11 驗證碼與登入狀態（老實說明）

與 0.3 的規範一致，不因為換一個系統就放寬：**不做 OCR、不接第三方辨識服務**。
使用者 2026-08-18 明確要求「直接幫我輸入驗證碼、繞過就繞過」，仍維持不做。

⚠ **「下次跑就免登入」在這個系統做不到**，兩種作法都實測失敗：

1. 存 cookie（`storageState`）再灌進新瀏覽器 → 隔 9 分鐘就被要求重新登入
2. 固定的瀏覽器使用者資料夾（`launchPersistentContext`）→ 仍然要重新登入

根本原因見 6.8 第二列：**主畫面是登入後動態切換出來的，重新開啟網址一律回到登入表單**，
與 cookie 還在不在無關。因此真正能省的只有：

- **一次登入把整份名單做完**（每位之間不重新登入，這是主力）
- 名單跑到一半被踢掉時，`ensureSignedIn()` 在**同一個視窗**請本人重登，做完的不必重來

程式碼仍保留固定資料夾的作法（無害，且換系統時可能有用），但不再宣稱能免登入。

### 6.13.1 「本來就有了」不要重做

第 7 輪試走發現受測對象的 `#MCI` 勾選框**本來就已勾選**。由此補了一條規則：
動手之前先讀現況（`readSubsystemState`），**已勾選且角色就是 MCI002 就直接結案**，
回報「本來就有了」，不再選一次、也不按確定——少按一次就少一次出錯機會。
其餘情況會在說明裡寫出「原本是什麼」，承辦人看得出誰是這次才開的。

> ⚠ 順序很重要：**先讀現況再動手**。反過來的話，選完就再也答不出
> 「這個人本來有沒有權限」，而那正是看名單時最想知道的一件事。

另外，後備定位路徑（`#MCIselect` 失效時才走）**不准點勾選框**：
那一列的第一個可按元素就是勾選框，點下去會把已經勾好的權限**取消掉**
（由測試抓到，見 `skipToggles`）。
