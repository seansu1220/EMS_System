## 1. 技術架構（沿用 Case_Control 模式）

| 層級 | 技術 |
| --- | --- |
| 前端框架 | React 19 + TypeScript |
| 建置工具 | Vite 6 |
| 樣式 | Tailwind CSS 4（響應式，手機優先） |
| 路由 | React Router 7 |
| 驗證 | Firebase Authentication（Email/密碼、Google） |
| 資料庫 | Cloud Firestore（即時同步） |
| 部署 | Firebase Hosting |

### 架構原則
- 職責分離：UI（components/pages）↔ 業務邏輯（services）↔ 狀態（hooks/context），services 不依賴 React。
- 型別先行：跨模組資料結構定義於 `src/types`。
- 配置驅動：狀態選項、優先度、提醒天數等常數集中於 `src/config`。
- 安全在資料庫層：Firestore Security Rules 限制只能存取自己的資料。

## 2. 功能規格

### 2.1 登入與帳號審核（v1.8 起）
- Email/密碼註冊登入 + Google 一鍵登入。
- **帳號審核制**：新註冊的帳號狀態為 `pending`（待審核），登入後只看得到「等待管理員核准」畫面，
  **完全無法讀取任何業務資料**（安全規則層阻擋）。管理員核准後畫面**自動解鎖**（即時訂閱 users 文件），
  不需重新登入。管理員可將帳號改為 `rejected`（拒絕/停用），該帳號即無法再進入系統（資料不刪除）。
- 註冊頁明示「新帳號需經管理員核准後才能使用」。
- **管理員以 email 白名單認定**（`ADMIN_EMAILS`，目前為 `seansu1220@gmail.com`），
  不是靠資料庫欄位，避免有人竄改自己的文件提權；該 email 註冊/登入時自動為 `admin` + `approved`。

### 2.1.1 權限模型（v1.8 起）
**資料範圍：全體已核准使用者共用同一批業務 / 屬性 / 待辦公版**（代理職務時可互相接手）。
`ownerUid` 欄位語意自 v1.8 起改為「**建立者**」，不再用於資料隔離。

| 動作 | 管理員 | 一般使用者（已核准） | **解鎖專用**（v1.17） | 待審核 / 未通過 |
| --- | --- | --- | --- | --- |
| 讀取業務、屬性、待辦公版 | ✅ | ✅ | ❌ | ❌ |
| 新增 / 編輯業務（含進度、待辦、完成/解除） | ✅ | ✅ | ❌ | ❌ |
| 新增 / 改名 / 排序屬性、新增與編輯待辦公版 | ✅ | ✅ | ❌ | ❌ |
| **刪除業務** | ✅ | ❌ | ❌ | ❌ |
| **刪除屬性**（v1.8.1 起） | ✅ | ❌ | ❌ | ❌ |
| **刪除待辦公版**（v1.8.1 起） | ✅ | ❌ | ❌ | ❌ |
| 使用者管理（核准 / 停用帳號 / 指派角色） | ✅ | ❌ | ❌ | ❌ |
| **提出解鎖工單**（v1.17 起） | ✅ | ✅ | ✅ | ❌ |
| **看得到所有人的解鎖工單** | ✅ | ✅ | ❌（只看自己送的） | ❌ |
| **回寫解鎖結果**（本機工具用這個身分） | ✅ | ✅ | ❌ | ❌ |

**「解鎖專用」角色**（v1.17 起，使用者 2026-08-06 指定）：權限最低，給各分隊申請解鎖用。
用這種帳號登入只進得去 `/unlock`，導覽列不顯示業務管理的任何入口，
連 Firestore 都讀不到業務資料。管理員與一般使用者則兩邊都能用、可自由切換。

角色**只能由管理員在使用者管理頁指派**：註冊時一律是 member/pending，不能自己選；
`admin` 也不在可指派清單內——管理員身分來自 email 白名單，改文件的 role 欄位並不會提權。

- 一般使用者的三個「刪除」按鈕（業務 / 屬性 / 公版）皆**不顯示**，即使繞過前端也會被 Firestore 規則擋下。
- 公版內「單一項目」的增刪改屬於編輯（update），一般使用者仍可操作；受限的是刪除整份公版。
- 前端判斷集中於 `src/lib/permissions.ts`（純函式），最終防線為 `firebase/firestore.rules`，兩者須一致。

### 2.2 首頁 `/`
**上方：近期任務提醒卡**
- 預設顯示「已逾期 + 剩 7 個工作日內到期」的項目，依期限由近到遠排序；
  點擊「展開」改顯示 30 個工作日內。
- 提醒來源兩種：①未完成業務的期限；②未勾掉的待辦事項（checklist）的期限，
  顯示時標註「待辦」並帶出所屬業務名稱。
- 顏色標示：已逾期＝紅色、剩餘工作日 3 天內＝橙色、其餘＝一般色；每筆顯示期限日期、
  剩餘/逾期天數、名稱、屬性標籤，點擊跳轉業務詳情。
- **剩餘天數以「工作日」計**（v1.11.8 起）：顯示「剩 N 個工作日」，N＝今天（不含）到期限（含）
  之間的工作日數。目的：避免週五看到下週一到期的業務時，因日曆日「剩 3 天」而誤判還有餘裕
  （實際只剩 1 個工作日）。已逾期仍以日曆日呈現（「逾期 N 天」）、期限為今天顯示「今天到期」；
  滑鼠停留於天數可看日曆日天數。
- **納入提醒的 7 / 30 天視窗同樣以工作日計算**（v1.18.2 起）：門檻集中於 `REMINDER_WORKDAYS`
  （default 7 / expanded 30 / urgent 3），三者單位一致，避免同一個「天」在視窗與顯示各代表一種算法。
  視窗判定為 `isWithinWorkdays()`，逐日掃描但一超過門檻即中止（遠期業務不必算到精確天數）。
  副作用：跨連假時視窗涵蓋的日曆日會變長（例：剩 7 個工作日可能橫跨 10 個日曆日），
  這正是預期行為——提醒的是「還有幾天能上班處理」。
- **工作日的定義**（v1.12 起）：預設週一～週五（`WORKDAY_WEEKDAYS`），再扣除國定假日、
  加回補班日，假日清單見 2.7。**清單未涵蓋的年份只扣週六日**，不猜假日；
  滑鼠停留於天數會註明該年度尚未匯入假日。計算集中於 `src/lib/workday.ts`（純函式）。
- **無期限且未完成的業務**：不受 7/30 個工作日的視窗限制，**永遠顯示**於提醒卡內，
  獨立區段排在有期限項目之後，灰色「未定期限」標籤區隔（避免被遺忘）。（v1.4 起）
- 已完成業務、已勾掉的待辦、無期限的待辦事項不進提醒。

**下方：業務列表**
- 屬性頁籤：「全部」+ 各屬性（依 sortOrder 排序），點選切換篩選。
- 「顯示已完成」開關（預設隱藏已完成）。
- 關鍵字搜尋（業務名稱 / 說明 / 備註）。
- 每筆顯示：業務名稱、屬性、期限（含逾期標紅）、未完成待辦數、最新一筆進度摘要；
  已完成業務顯示「已完成」徽章。
- 排序：未完成在前；未完成之中**無期限的排最上面**（易被遺忘，優先曝光），
  其後依期限近到遠，再依 updatedAt。（v1.4 起；v1.3 前為無期限排最後）
- 「新增業務」按鈕。

### 2.3 業務管理（CRUD）
| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| title | string | 業務名稱（必填） |
| categoryId | string | 屬性（下拉選擇，必填；選單內含「＋新增屬性」可即時建立並選取） |
| description | string | 業務說明 |
| deadline | string \| null | 期限（yyyy-MM-dd，可空＝無期限） |
| progressEntries | array | 進度紀錄（見下） |
| checklistItems | array | 待辦事項清單（見下） |
| note | string | 備註 |
| completed | boolean | 是否完成（完成後鎖定） |
| completionDate | string \| null | 完成日期（yyyy-MM-dd） |
| completionTime | string \| null | 完成時間（HH:mm，可空） |
| completionNote | string | 完成說明 |
| ownerUid | string | 擁有者 |
| createdAt / updatedAt | timestamp | 系統時間 |
| completedAt | timestamp \| null | 標記完成時間 |

（v1.1 起不再有優先度 priority 與狀態 status 欄位；業務只分「進行中 / 已完成」。）

**progressEntries 項目**：`{ id, date (yyyy-MM-dd, 日期選擇器), time (HH:mm | null, 時間選擇器可空), content, createdAt }`
- 由新到舊顯示（日期新→舊，同日依時間新→舊，無時間排該日最後），可新增 / 刪除單筆。

**checklistItems 項目（待辦清單）**：`{ id, content, deadline (yyyy-MM-dd | null), done, sortOrder, createdAt }`
- 主進度之外的小問題 / 支線事項，亦用於拆解**標案等多流程業務**的每個關卡。
- 可新增（內容 + 可選期限）、**編輯（內容與期限，v1.7 起）**、勾選完成、刪除。
  期限可先留空（一開始不知道期限），之後按「編輯」補上或清除。
- **勾選完成時跳出確認對話框**「是否將此待辦寫入進度紀錄？」：確定則同一次寫入中
  將該項 done=true 並新增一筆進度（date=今天、time=當下時:分、content=「完成待辦：<內容>」）；
  取消則僅勾選。取消勾選（復原）不跳對話框。
- **已勾掉的項目預設隱藏**，區塊底部提供「顯示已完成（N）」切換按鈕展開/收合。
- 未勾掉且有期限者進首頁提醒卡（標註「待辦」）。
- **排序模式（v1.7 起）**可切換：
  - 「流程順序」（預設）：依 sortOrder，已勾項目留在原位；未鎖定時可**拖曳左側把手**調整
    （桌機滑鼠、手機長按 200ms），放開後批次寫入 sortOrder（0..n-1）。
  - 「依期限」：未勾在前（期限近到遠，無期限在後），已勾在後（顯示刪除線）。
- **完成進度條（v1.7 起）**：區塊上方顯示「已完成 N / 總數（百分比）」與進度條。
- 逾期未勾以紅色、**剩餘 3 個工作日內**以橙色標示期限（v1.18.2 起與提醒卡同一套工作日算法，
  改版前為日曆日）；無期限者顯示灰色「未定期限」。

**期限展期（業務詳情頁編輯表單，期限欄旁）**
- 已有期限且未鎖定時顯示「展期」按鈕；點擊展開天數選擇（快選 +1 / +3 / +7 天與自訂天數）。
- 確認後期限 = 目前期限 + N 天，並**立即儲存整張表單**（含其他未儲存的欄位修改），不需再按儲存變更。
- 無期限的業務不顯示展期按鈕（先在期限欄選日期即可）。

**完成區塊（業務詳情頁獨立區塊）**
- 填完成日期（預設今天）＋ 完成時間（HH:mm，預設當下，可空）＋ 完成說明，
  按「標記完成」並二次確認 → `completed = true`、記錄 completedAt，
  業務**鎖定**：所有欄位、進度、待辦皆不可修改。
- 已完成業務顯示完成資訊（日期 時間 說明）與「解除完成」按鈕；解除（二次確認）後恢復可編輯，
  completed 改 false、completedAt 清空（completionDate / completionTime / completionNote 保留供參考）。

- 刪除業務需二次確認（未鎖定時才可刪除）；**刪除按鈕僅管理員可見**（v1.8 起，見 2.1.1）。
- 表單儲存成功後按鈕須恢復可按狀態，並短暫顯示「已儲存」提示。

窄螢幕自動改為上下堆疊，屬性在上。兩區塊各自管理狀態與錯誤訊息，互不影響。

- 預設屬性：採購、系統、其他（系統首次使用時自動建立；屬性為全體共用，只建立一次）。
- 可新增、改名、排序（所有已核准使用者）；**刪除僅管理員**（v1.8.1 起，按鈕對一般使用者不顯示）。

### 2.4.1 假日設定（屬性管理頁右欄，v1.12 起）
決定首頁「剩 N 個工作日」要扣掉哪些日子。**所有已核准者可查看，只有管理員能匯入或刪除**
（這份資料會改變每個人看到的天數）。元件為 `src/components/HolidaySettings.tsx`。

**資料來源與涵蓋範圍**
- 程式內建 2026、2027 兩年（`src/config/holidays.ts`），由行政院人事行政總處
  「政府行政機關辦公日曆表」開放資料（政府資料開放平臺 dataset 14718）的官方 CSV 轉出。
- 政府通常每年年中才公布次年日曆表，故內建清單天生只涵蓋近一兩年；
  新年度公布後由管理員匯入，**不需重新部署程式**。未涵蓋年份退回「只扣週六日」。

**儲存格式**：只存「與預設不同的例外日」，不存整年 365 天——
`holidays[]`＝平日卻放假（國定假日、補假），`workdays[]`＝週末卻要上班（補班日）。
一年約 20 筆，資料量小且可人工核對。

**匯入流程**：選擇官方 CSV 檔案（或貼上內容）→ 系統解析後顯示「讀到幾天假、哪幾天」的預覽
→ 確認後才寫入 Firestore → 全裝置即時生效。同一年重複匯入會直接覆蓋，不會留下兩份打架的資料。

**解析規則**（`src/lib/holidayCsv.ts`，純函式）
- 官方數字版格式：`西元日期,星期,是否放假,備註`，是否放假欄 `0`＝上班、`2`＝放假。
- 日期容錯接受 `20270101` / `2027-01-01` / `2027/1/1` 三種寫法；不存在的日期（如 2 月 30 日）略過。
- **整年不足 350 天的年度一律拒絕匯入**並說明原因——寧可不匯，也不要匯進殘缺清單而漏算假日。
- 檔案完全讀不到日曆資料時，明確提示可能選到 Google 行事曆專用版或 PDF。

### 2.5 待辦公版 `/templates`（v1.7 起）

把常做的一套流程（例如標案的各關卡）存成公版，重複套用到新業務，不必每次重打。

- **資料**：`checklistTemplates/{id}` = `{ name, items: [{ id, content, sortOrder }], ownerUid, createdAt, updatedAt }`。
  公版**只保存項目內容與順序，不含期限與勾選狀態**（期限於套用後個別編輯）。
- **管理頁**：新增公版（名稱）、改名；公版底下項目可新增、改內容、刪除、拖曳排序。
  **刪除整份公版僅管理員**（v1.8.1 起，按鈕對一般使用者不顯示）。
- **建立公版的兩種方式**：①管理頁新增空白公版後逐筆加項目；
  ②業務詳情頁待辦區塊「另存為公版」，把目前待辦內容（依流程順序）存成新公版。
- **套用公版**：
  - 新增業務頁：選一個公版，建立業務時自動帶入為初始待辦（期限留空）。
  - 業務詳情頁待辦區塊：選公版按「套用公版」，**附加**到現有待辦之後（不覆蓋既有項目），二次確認。
- 刪除公版不影響已套用到業務上的待辦事項。

### 2.8 解鎖工單頁 `/unlock`（v1.17）

**上半：提出申請。** 貼上 TEMSIS（一行一個，也接受從 Excel 整欄複製；重複的只留一筆）
＋填申請事由（標題後方提示「請填寫解鎖後欲修改內容」）→ 送出。一個編號建立一張工單，一次最多 50 筆（防手殘誤貼整欄）。

**長度檢查（v1.19）。** TEMSIS 碼固定 **22 碼**（`TEMSIS_CODE_LENGTH`，例：`2026090710100307554102`）。
輸入框邊打邊檢查，**每一個長度不對的編號各列一行**：

> `2026090710100307554`：TEMSIS碼長度為 22 碼，目前輸入號碼長度為 19 碼，請提供正確TEMSIS碼

在有錯的期間「送出申請」按鈕停用；`createUnlockRequests()` 送出前也再擋一次（同一句訊息）。
原因：長度不對的編號送出去，要等救護科電腦跑完回「查無案件」才知道打錯，白等一輪
（使用者 2026-09-07 指定）。**只檢查長度**，不檢查編號真的存不存在——那要連上目標系統才知道。

**下半：工單清單。** 即時更新，新的排前面。管理員與一般使用者看得到全部（多一欄「申請人」），
解鎖專用帳號只看得到自己送的。每一筆顯示狀態、TEMSIS、事由與結果：

| 狀態 | 顯示 | 結果欄給申請人看的一句話 |
| --- | --- | --- |
| `pending` | 待處理 | 等救護科電腦執行 |
| `running` | 處理中 | 正在處理… |
| `unlocked` | 已解鎖 | 已解鎖，可以進系統修改了 |
| `usageCleared` | 已解除佔用 | 本來就是未結案，但還有人開著；已經幫你放開，可以進系統修改了 |
| `noAction` | 案件未結案 | 案件未結案，不需解鎖。有問題請洽救護科承辦人 |
| `failed` | 需人工處理 | 請洽救護科承辦人處理 |

**`usageCleared` 是第二種解鎖方式的結果**（v1.20，使用者 2026-09-11 指定）。
有些案件**本來就是未結案**（紀錄表後面沒有那個「鎖」字），分隊卻還是進不去改——
卡住的原因不是結案鎖，而是那份紀錄表**還被某台裝置線上使用中**。
救護科電腦判到「沒有鎖頭」時會自動改走第二條路：到目標系統的
「系統設定 → 線上使用狀況」找出那一筆佔用紀錄並刪掉（完整作法見
[TOOLS_SPEC.md](TOOLS_SPEC.md) 2.11）。

刻意**不與 `unlocked` 合併**：對申請人來說結果一樣是「可以去改了」，
但救護科實際動的是完全不同的地方，事後回頭核對要分得出來。
也因為多了這一步，`noAction` 的意思跟著收窄——現在要**紀錄表沒鎖頭、
而且線上使用狀況裡也查不到佔用紀錄**，才會回報「案件未結案，不需解鎖」。

**結果欄分兩種詳細度**（v1.18.3 起，使用者 2026-08-09 指定）：

- **所有人**：案件日期＋出勤車輛（分隊）、上表那一句話、處理時間與執行者。
  足夠確認「是不是我那件、現在能不能去改」。
- **管理員另外看得到「執行細節」**：本機工具回寫的 `result.detail` 原文
  （第幾張紀錄表、比對到哪個解鎖按鈕、畫面出現什麼訊息）。
  那是維護時才用得到的東西，對分隊只是雜訊；要追整個過程請看執行電腦的
  `tools/ems-report/out/watch.log`，比這一欄清楚得多。
  一句話的對照表集中在 `src/config/constants.ts` 的 `UNLOCK_RESULT_SUMMARY`。

**管理員專屬的兩個動作**（v1.18.3 起，每一列各一顆按鈕，按下前都會再確認一次）：

| 動作 | 效果 | 什麼時候用 |
| --- | --- | --- |
| **重新送單** | 狀態退回 `pending`、`result` 清空，救護科電腦下一輪會再跑一次 | 解鎖流程本身出過狀況（例如頁面沒載完被誤判成「查無案件」），案件其實沒問題 |
| **刪除** | 整張工單刪掉，**無法復原** | 誤送、重複送、或已經人工處理完不需要留著 |

「待處理」的工單不需要重新送單，該按鈕會停用。兩個動作都只有管理員做得到——
刪除由安全規則擋住（`allow delete: if isAdmin()`），重新送單則是介面層限制
（規則層允許 `isStaff()` 更新，因為那正是本機工具回寫結果用的身分）。

> ⚠ **這一頁不會真的去解鎖。** 目標系統要驗證碼、瀏覽器也無法跨網域操作那套 frameset 系統，
> 因此網頁只負責申請與查結果，實際動手的是救護科電腦上的本機工具
> （完整原因與流程見 [TOOLS_SPEC.md](TOOLS_SPEC.md) 第 5 章）。

### 2.9 測試用傷票領取頁 `/triage-tags`（v1.21）

給同仁領取「大量傷患檢傷追蹤卡」測試用傷票（使用者 2026-09-21 指定）。
**三種角色都能用**，解鎖專用帳號登入後導覽列上的第二個標題就是這一頁。

**號碼規則。** 格式 `H` + 2 碼 + `T` + 3 碼，範圍 `H00T000 ~ H99T999`，共 10 萬張。
內部用流水號 0 ~ 99999 記帳（`H01T234` ＝ 1234），**全系統接續發放**：
A 領 10 張拿到 `H00T000 ~ H00T009`，下一個人領 2 張就是 `H00T010`、`H00T011`。
號碼一旦發出**不回收**（同紙本傷票，印壞了就作廢）。一次最多 100 張
（`TRIAGE_TAG_MAX_PER_REQUEST`，防手殘多打一個 0；規則層同步限制）。

**單位與每週上限（v1.22，使用者 2026-09-21 指定）。**
- 領取時**必填單位**，用**下拉選單**選，**只限月報表上的 41 個分隊**（v1.23，依大隊分組；
  `TRIAGE_TAG_BRIGADES`，照抄 `tools/ems-report/config.mjs` 的 `BRIGADES`）。
  不在名單上的一律不給領（前端與安全規則都擋）。名單固定也避免同一個分隊有不同寫法而被算成不同單位、繞過每週上限。
  ⚠ 分隊有異動時三處要一起改：`src/config/triageTag.ts`、`tools/ems-report/config.mjs`、
  `firebase/firestore.rules` 的 `triageUnitValid()`。
  （v1.22 原本是「兩個中文字＋分隊」的格式檢查，v1.23 改為名單。）
- **管理員專用單位「救護科」**（v1.24，使用者 2026-09-21 指定；`TRIAGE_TAG_ADMIN_UNIT`）：
  只有管理員的下拉選單會多出「科內（管理員）→ 救護科（不限張數）」，**不受每週上限**；
  單次仍最多 100 張（PDF 太大瀏覽器會卡），要更多就分次領。用量一樣記在單位週用量裡，方便日後查。
  管理員選一般分隊時照樣受每週 30 張限制。規則層同步限制（非管理員送救護科會被擋）。
- **同一單位每週最多 30 張**（`TRIAGE_TAG_UNIT_WEEKLY_LIMIT`；v1.22～v1.27.0 為 20 張，v1.27.1 起放寬為 30 張）。「一週」是台灣時間
  **週一 00:00 ～ 週日 23:59**，每週一歸零。輸入單位後畫面即時顯示
  「本週（9/21（一）～ 9/27（日））大湳分隊 已領 12 / 30 張」；超過時顯示還能領幾張並停用送出。
  上限算的是**單位**，不看是哪個帳號領的。
- 瀏覽器會記住上次選的單位（localStorage，只是方便，不影響判斷；不在名單上的舊值不帶入）。

**畫面。**
- 上半：輸入單位與張數 → 「領取並下載 PDF」。旁邊即時顯示「下一張從 H00T0xx 開始、還剩幾張」。
  按下後先發號、再在瀏覽器裡產生 PDF 並下載，按鈕上顯示「產生 PDF 中… 3 / 10 頁」。
- 中間：列印方式說明（3 點：A4 印兩張正背交錯、雙面長邊翻轉＋實際大小、沿虛線剪下）。
- 領取按鈕旁的「**重新下載**」（v1.23）：領到號碼後才出現，**只能重新下載本頁剛領的那一批**
  （號碼不變、不會再發新號），給當下沒載到或產生失敗的人補救。只記在畫面上，
  離開或重新整理頁面就消失。
- 下半：領取紀錄（新的排前面，含「單位」欄），**只列紀錄、不提供下載**（v1.23 起）——
  避免之後登入的人把別人領的傷票載走（使用者 2026-09-21 指定）。
  管理員與一般使用者看得到全部（多一欄「領取人」），解鎖專用帳號只看得到自己的。

**PDF 版面。** 照紙本傷票重畫（`src/lib/triageTagDraw.ts`），一張 A4 直式左右並排兩張，
每張 95 × 285 mm、外框畫淺灰虛線當裁切線：

| 面 | 內容 |
| --- | --- |
| 正面 | 掛繩孔、「檢傷追蹤」、右上可撕的「後送存根」斜角（QR code＋號碼）、姓名（不詳）、男/女/不明、約＿歲、補充說明框 |
| 背面 | 左上可撕斜角（直立號碼、時間/醫院/車輛灰底欄、四色小方格）、「檢傷追蹤」＋ QR code、人形圖正面/背面、時間/呼吸/脈搏/血壓表（3 列） |
| 兩面共用 | 0（黑，內含 Code128 條碼＋號碼）／ I（紅）／ II（黃）／ III（綠）四條色帶，色帶間畫撕線；最底下灰色存根條（直書「檢傷沿線撕下」＋ QR code；正面右側性別年齡、背面右側「檢傷存根」） |

QR code 與條碼的內容都是傷票號碼本身（例 `H00T010`）。

**雙面對齊。** PDF 頁序為「正面、背面」交錯；**背面頁的左右是對調的**——
印表機選「雙面列印 → 長邊翻轉」時紙翻過來左右互換，正面左邊那張的背面要畫在背面頁右邊才會疊在一起。
張數為奇數時最後一張 A4 只有一張：正面在左、背面在右。
列印須選「實際大小（100%）」，不可「符合頁面」，否則正反面會錯位。

**實作。** 每一頁先用 canvas 畫（中文字用瀏覽器現成字型，不必在 PDF 嵌入字型檔），
以 250dpi JPEG 放進 jsPDF（每頁約 320 KB）。PDF 模組（jsPDF、qrcode、jsbarcode）**只在按下載時才載入**，
不拖慢其他頁面。尺寸、解析度、色碼、上限集中在 `src/config/triageTag.ts`。

**發號的一致性。** 「讀計數器與單位本週用量 → 往後推 → 寫領取紀錄」包在同一個 Firestore transaction
（`triageTagService.allocateTriageTags`），兩人同時按也不會拿到同一批號碼、也不會一起衝破單位上限；
安全規則再用 `getAfter` 互相核對三份文件（見第 3 章安全規則）。

（使用者 2026-10-27 指定：放一次檔案就能做各種操作，不用每做一件事重丟一次；SelfWeb 同步改版）。
**檔案全程只在瀏覽器記憶體處理，不上傳、不寫 Firestore、沒有安全規則異動**，
因此三種角色都能用，可放心處理含個資的救護紀錄與公文。

**小工具頁的分區。** 所有人都看到「PDF 工具」；管理員右上角多一個切換，

切去看說明或紀錄再回來，PDF 工作區裡的檔案不會消失。舊版的 `#merge` 等書籤一律顯示 PDF 工具。
小工具頁用寬版面（`Layout` 依路徑把內容寬度由 1024px 放寬到 1800px），大圖才有空間。

**使用紀錄（v1.29，使用者 2026-10-27 指定「記錄有誰使用過，30 日內」）。** 每按一次下載（四種方式皆是）

第一次切到這一區才開始讀資料庫。

**工作區的版面**（電腦寬度；手機寬度時改為上下排列，工具列變橫排、頁面清單變橫向捲動）：

**復原。** 加入檔案、移除檔案、排序、轉向、刪除、加／刪標記都可以「復原上一步」（最多 50 步，
`PDF_WORKSPACE_CONFIG.historyLimit`），復原時連當時的勾選一起還原（例如復原刪除，回來的頁仍是勾選狀態）。
鍵盤：Ctrl＋Z 復原、Delete 刪除頁面（在輸入框打字時不作用）。

**標記座標與旋轉。** 標記存成頁面上的 0～1 比例，以「原方向」（已套用 PDF 本身的 /Rotate、不含工作區加的旋轉）為準；
大圖上畫的框先換回原方向再存，所以**先畫標記、之後再轉頁面，標記會跟著轉**。換算為純函式（`lib/pdfEditLogic.ts`）。

**輸出規則（真正的遮蔽）。** 所有下載方式都走同一支（`lib/pdfWorkspaceExport.ts`）：
- 有**塗黑或馬賽克**的頁面：依大圖的方向，整頁以約 180 dpi（`exportScale` 2.5，長邊上限 5000 px）畫成圖片、
  套上標記後以 JPEG 放回，**該頁原本的文字、隱藏圖層、註解全部消失**——只蓋一個黑框的話，
  底下文字其實還在，複製貼上就看得到。代價是那幾頁文字不能再選取、搜尋，畫面上會提示。
- 只有**螢光筆**的頁面：保留原本的向量內容（文字仍可選取、搜尋），以「色彩增值」疊上色塊；
  先用 `translateContent(0,0)` 把原內容包進 q…Q，再另開新的內容串流畫，原檔沒還原座標狀態也不會畫歪。
  座標經 pdf.js `convertToPdfPoint` 換算，PDF 本身旋轉過的頁面一樣準；之後再套用工作區加的旋轉。
- 沒有標記的頁面原樣複製並套用旋轉。同一個來源檔要複製的頁一次複製，字型等共用資源不會重複。
- 繪製順序固定為螢光筆 → 馬賽克 → 塗黑，遮蔽一定在最上層。畫面與輸出共用同一支繪圖函式（`lib/pdfMarkPaint.ts`）。
  馬賽克格子＝頁寬的 1/45（刻意比一般內文字高大），以逐次減半縮小取平均色。

**轉 PDF 小技巧。** PDF 工具下方有可展開的「網頁、文件要變成 PDF？不用印出來再掃描」，
列出電腦（另存為 PDF、Microsoft Print to PDF）、iPhone、Android、紙本（手機掃描）的做法，
內容在 `config/pdfTools.ts` 的 `PDF_CONVERT_TIPS`，新增情境即加一筆。

**檔名規則。** 檔名中的 `\ / : * ? " < > |` 一律換成 `_`；勾選下載為「檔名_勾選N頁.pdf」，
拆分為「檔名_第1-3頁.pdf」（ZIP「檔名_拆分.zip」），各檔分開的 ZIP 為「檔名_各檔.zip」，ZIP 內同名檔自動加序號。

**實作。** pdf-lib 負責組出新 PDF 與圖片嵌入，pdf.js（legacy 版，相容較舊的瀏覽器）畫縮圖與大圖，JSZip 打包。
縮圖捲到附近才畫（`IntersectionObserver`），大圖最近 8 張留快取。清空或離開頁面時關閉所有 pdf.js 文件釋放記憶體。
PDF 工作區以 `React.lazy` 延遲載入，**只有進小工具頁才下載這些函式庫**，不拖慢其他頁面。
pdf.js 讀檔需要的資源（`cmaps` 中文字型對照表、`standard_fonts`、`wasm` 掃描檔影像解碼器、`iccs` 色彩描述檔，
約 3.8 MB）由 `vite.config.ts` 每次啟動／建置時從 `node_modules/pdfjs-dist` 複製到 `public/pdfjs/`
（gitignore），隨網站部署、檔案用到才下載。**少了 `cmaps`，未內嵌中文字型的公文會整頁空白**（v1.27 修正）。
檔案拖到拖放區外時攔下瀏覽器預設行為，避免直接開啟該檔而離開本頁。

模組分工：工作區狀態 reducer 與下載規劃為純函式（`lib/pdfWorkspace.ts`）；標記與旋轉換算（`lib/pdfEditLogic.ts`）；
頁碼解析與檔名（`lib/pdfPageLogic.ts`）；讀檔、圖片轉 PDF、打包（`lib/pdfEngine.ts`）；繪圖（`lib/pdfRender.ts`、`lib/pdfMarkPaint.ts`）；
輸出（`lib/pdfWorkspaceExport.ts`）；來源檔管理 hook（`hooks/usePdfWorkspace.ts`）；
畫面元件在 `components/pdf/`（`PdfToolbox` 組版面，`WorkspaceFileBar`、`WorkspaceToolbar`、`WorkspacePageList`、
`WorkspaceViewer`、`WorkspaceExportPanel`、共用的 `PdfToolParts`）。
縮圖與大圖尺寸、A4、留白、復原步數、來源色、輸出解析度、馬賽克大小等參數集中在 `config/pdfTools.ts`。
套件安全更新的檢查方式見 TODO.md「定期安全更新」（`npm run deps:check`）。

## 3. 資料模型（Firestore）

- `users/{uid}`：{ uid, email, displayName, **role**（admin/member/**unlocker**）, **status**（pending/approved/rejected）,
  **reviewedAt**, **reviewedBy**, createdAt }（粗體為 v1.8 新增）
- `categories/{id}`：{ name, sortOrder, ownerUid（建立者）, createdAt }
- `tasks/{id}`：見 2.3 欄位表（ownerUid 為建立者）
- `checklistTemplates/{id}`：見 2.5（待辦公版）
- `holidays/{西元年}`：{ year, holidays[]（{date,name}）, workdays[]（{date,name}）,
  offDayCount（全年放假天數，供人工核對）, updatedBy, updatedAt }（v1.12 新增，見 2.7）
  ——文件 ID 就是年份，重複匯入同年直接覆蓋。
- `unlockRequests/{id}`（v1.17 新增）：{ temsis, reason, requestedBy, requestedByName, requestedAt,
  status（pending/running/unlocked/**usageCleared**/noAction/failed）, result（{caseDate, vehicle, squad, detail,
  processedAt, processedBy} 或 null）}
  ——**一個 TEMSIS 一張工單**。網頁只負責申請與查結果，實際解鎖由本機工具執行後回寫，
  原因與完整流程見 [TOOLS_SPEC.md](TOOLS_SPEC.md) 第 5 章。
  ⚠ 這是「個案編號上雲」的**唯一例外**（只有編號、事由與結果，沒有任何病患資料），
  取捨說明見 TOOLS_SPEC 0.3。
- `triageTagCounter/main`（v1.21 新增）：{ nextSerial（下一個要發的流水號，0 ~ 100000）, updatedAt }
  ——全系統只有這一份，測試用傷票的號碼從這裡接續往下發（見 2.9）。
- `triageTagIssues/{起始流水號}`（v1.21 新增）：{ startSerial, count, **unit**, **weekIndex**, requestedBy, requestedByName, requestedAt }
  ——一次領取一筆，文件 ID 就是起始流水號（不補零，例 `10` ＝ `H00T010` 起），天生不重複。
  （粗體為 v1.22 新增）
- `pdfToolUsage/{自動 ID}`（v1.29 新增）：{ uid, userName, email, action（`downloadAll`／`downloadSelected`／`perSource`／`split`）,
  pageCount, fileCount, sourceCount, markedPages, usedAt（伺服器時間） }——PDF 工具每次下載一筆，**不含檔名**，保留 30 天（見 2.10）。
- `triageTagUnitWeeks/{週序}_{單位}`（v1.22 新增）：{ unit, weekIndex, used（本週已領張數）, lastStartSerial }
  ——某單位某一週的領取量，例 `2960_大湳分隊`。週序＝台灣時間的本地日序加 3 除以 7 取整
  （1970-01-01 是星期四，這樣剛好每個週一跳號；前端 `triageTagWeekIndex()` 與規則 `triageWeekIndex()` 同算法）。
  `lastStartSerial` 記最後一次加量的那張領取紀錄起始號，給安全規則核對用。

### 安全規則（v1.8 改版）
- 管理員以 `request.auth.token.email` 比對白名單認定（**不讀資料庫欄位**，避免竄改文件提權）；
  白名單須與 `src/config/constants.ts` 的 `ADMIN_EMAILS` 手動保持一致。
- `tasks` / `categories` / `checklistTemplates`：
  讀取與更新須為 `isStaff()`＝已核准**且不是「解鎖專用」**（v1.17 起，原本只看已核准）；
  建立另強制 `ownerUid == request.auth.uid`（記錄建立者）；
  **三者的 delete 皆僅管理員**（v1.8.1 起）。
- `holidays`：`isStaff()` 可讀（首頁計算天數要用），**寫入與刪除僅管理員**（v1.12 起）。
- `unlockRequests`（v1.17 起）：
  - 讀：`isStaff()` 看全部；其他已核准帳號**只讀得到 `requestedBy == 自己`** 的。
    這一條同時管住 list——Firestore 要求查詢本身證明得出結果都合規，
    因此解鎖專用帳號**必須**帶 `where('requestedBy','==',uid)` 才查得動。
  - 建立：任何已核准帳號皆可，但強制 `requestedBy == 自己`、`status == 'pending'`、
    `temsis` 非空字串——不能替別人送，也不能直接送一張「已解鎖」的假工單。
  - 更新（回寫結果，以及管理員的「重新送單」）：僅 `isStaff()`，
    且不可竄改 `temsis`／`reason`／`requestedBy`／`requestedAt`。
  - 刪除：僅管理員。
- `triageTagCounter` / `triageTagIssues` / `triageTagUnitWeeks`（v1.21 起；單位週用量 v1.22 起）：
  - 讀：計數器任何已核准帳號可讀；領取紀錄 `isStaff()` 看全部，其他已核准帳號只讀得到自己的
    （同解鎖工單，查詢須帶 `where('requestedBy','==',uid)`）。
  - 領取：任何已核准帳號（含解鎖專用），但**計數器與領取紀錄必須在同一筆寫入裡一起寫**，
    規則用 `getAfter` 互相核對：紀錄的起始號＝計數器原本的下一號（不能挑號碼、不能重複領）、
    計數器推進的張數＝紀錄的張數（不能跳號、不能只推計數器不留紀錄）、
    `requestedBy == 自己`、張數 1 ~ 100、不超過 `H99T999`。
  - 單位（v1.22 起）：規則同樣檢查單位在月報表分隊名單內（v1.23 起，`unit in [...]`）、週序等於**伺服器時間**的這一週；
    單位週用量必須在同一筆寫入裡被這張紀錄更新（`lastStartSerial` 對得上）、加的量＝紀錄張數、加完 ≤ 20。
    單位週用量任何已核准帳號可讀（只有數字），刪除僅管理員。
    「救護科」只有 `isAdmin()` 能用，且用量不受 ≤ 20 限制（v1.24）。
  - ⚠ 規則每筆批次寫入最多讀 20 份文件，三份文件互相核對時要刻意省讀取（計數器與用量的舊值直接用 `resource`）；
    另外規則的 `math.floor` 回傳小數，組文件 ID 前必須 `int()`，否則會組出 `2960.0_大湳分隊`。
  - 領取紀錄不可修改，刪除僅管理員（號碼不回收）；計數器**任何人都不可刪除**（刪了號碼會從頭重發）。
- `pdfToolUsage`（v1.29 起）：建立＝任何已核准帳號（三種角色都用得到 PDF 工具），但欄位只准上述九個（`keys().hasOnly`，
  **多一個檔名欄位就擋**）、`uid` 必須是自己、`email` 必須等於登入 token 的 email、下載方式限四種、
  頁數／檔案數為 1 以上整數、`usedAt == request.time`（不能偽造時間）。讀取與刪除僅管理員；任何人不可修改。
- `users`：本人可讀自己的文件、可改自己的一般欄位，但 **role 與 status 不可自行變更**（不可自我核准/提權）；
  列出全部帳號與變更他人狀態僅限管理員；建立時強制
  `role/status == (管理員 email ? admin/approved : member/pending)`。
- 規則測試腳本置於 `scripts/rules.test.mjs`，執行 `npm run test:rules`（v1.29 起 **98/98 通過**，含測試用傷票 31 項、PDF 使用紀錄 15 項）。
  啟動器 `scripts/run-rules-test.mjs` 會自動找出 JDK 21 以上的安裝並只在該次執行插入 PATH——
  因為 firebase-tools 是直接呼叫 PATH 上的 `java`（不看 JAVA_HOME），而本機另有舊版 Java 8 排在前面。
  測試套件 `@firebase/rules-unit-testing` 刻意不列入 devDependencies（避免 peer 版本衝突），
  缺少時啟動器會提示安裝指令。

## 4. 本機小工具

小工具是**獨立於本網頁系統的本機 CLI**，
不參與 `npm run build`、不部署上線；網頁 `/tools` 頁的「電腦端工具說明」分區只放使用說明，
**v1.27 起只有管理員看得到**（其他人進小工具只看到 PDF 工具，見 2.10）。

說明分區（`components/LocalToolsGuide.tsx`）是**配置驅動**的：工具清單放在 `config/localTools.ts` 的 `LOCAL_TOOLS` 陣列，
每筆有標題、用途、捷徑檔名、操作步驟與選填的提醒，新增工具就加一筆。目前七項：

| 說明頁項目 | 對應捷徑 |
| --- | --- |
| 月度報表輸出（每個月就用這一個） | `捷徑\月度報表輸出.bat` |
| 到院前預警比率 | `捷徑\救護預警統計.bat` |
| 12 導程心電圖到院前傳輸率 | 含在月度報表輸出裡 |
| 二級以上因交通事故救護案件（來文格式一覽表） | `捷徑\二級以上因交通事故救護案件\產出來文格式.bat` |
| 未結案案件統整 | `捷徑\未結案案件統整.bat` |
| 解鎖救護紀錄表 | `捷徑\解鎖救護紀錄表.bat`（試跑）／`正式解鎖救護紀錄表.bat` |
| 線上解鎖工單（處理網頁上的申請） | `捷徑\線上解鎖工單.bat`（一次性）／`線上解鎖工單-自動監看.bat`（常駐） |

> 這一頁**不呈現也不儲存任何查詢結果**——工具會接觸個案明細，資料全程只留在使用者電腦。
> 說明文字提到產出檔時，一併寫明**哪些能發給分隊、哪些只能自己看**
> （例如到院前未預警清冊含完整 TEMSIS，落在 `out\internal`），
> 避免有人照著說明把含個資的檔案整份轉寄出去。

細部規格、目標系統結構、模組職責與維護注意事項另見 **[TOOLS_SPEC.md](TOOLS_SPEC.md)**，
以免本檔被工具細節淹沒。

## 6. 環境設定與部署

1. Firebase 主控台建立新專案，啟用 Authentication（Email/密碼 + Google）與 Firestore。
2. 複製 `.env.example` 為 `.env`，填入 Firebase 網頁設定碼。
3. `npm install` → `npm run dev`（本機開發用；使用者日常一律直接開線上網址，
   原本的「啟動業務管理系統.bat」捷徑因此於 2026-08-02 移除）。
4. 部署：`npm run build` → `npx firebase-tools deploy`，取得 `https://<專案ID>.web.app`，手機直接開啟。
