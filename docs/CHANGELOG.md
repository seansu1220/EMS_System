## 2026-08-10　v1.18.6 診斷指令答得出「分母多的那一件是哪一件」

### 問題描述
平鎮分隊來問：報表寫他們 7 月「要做 EKG 處置」是 10 件，但他自己在系統查只找到 9 件，
想知道我們的搜尋條件是什麼。

心電圖報表的分母是**聯集**——「有勾 EKG檢查」**或**「有 12 導程心電圖」，
所以它必然比任何單一條件都多，分隊只用其中一個條件自己查一定會少。
問題是診斷指令 `ekg-diag` 只印得出「勾了 EKG檢查但沒有 12 導程：N 件」這個**數字**，
沒有列出是哪些案件，回答不了「那一件是哪一件」，只能再登入一次重查。

順帶查出一個沒被發現的問題：`ekg-diag` 產出「有處置未勾選清冊」時用的是
**不限救護狀態／送醫情形**的 A、B 兩份資料，但正式報表用的是「已結案＋送醫」。
兩者**檔名完全相同**，所以跑一次診斷就會把正式流程產出的那份蓋掉，
換成一份數字對不起來的版本。

### 根本原因
1. 差集只做了單向（12 導程 − EKG檢查），反方向只算件數不留清單——
   當初的用途是查「漏勾處置」的成因，沒想到之後會有分隊來對數字。
2. 診斷段落沿用一開始寫的 A／B（不限狀態），而正式流程後來（v1.16.4）
   改成限定「已結案＋送醫」時，沒有一起改過來。

### 修改內容
- `tools/ems-report/ekgLists.mjs`
  - 兩份差集清冊版面相同，抽出 `buildTallyWorkbook()` / `writeTallyList()` 共用，
    大標與件數欄的用語跟檔名放在同一個常數（`MISSING_PROCEDURE_LIST`、`EKG_ONLY_LIST`），
    改名時不會出現「檔名是新的、大標還是舊的」
  - 新增 `writeEkgOnlyList()` / `buildEkgOnlyWorkbook()`，產出
    **`心電圖-有EKG處置無12導程清冊-{YYYY-MM}.xlsx`**（各分隊件數＋逐案清單，含完整 TEMSIS）
  - `buildMissingProcedureWorkbook()` / `writeMissingProcedureList()` 改為委派，行為不變
- `tools/ems-report/ekgDiagnose.mjs`
  - 第四段（交叉分析）維持用 **A／B（不限狀態）**——資料先篩成「已結案＋送醫」的話，
    救護狀態與送醫情形每一件都長一樣，分析不出東西；這一段不再寫檔
  - 新增第五段 `reportDenominatorParts()`：用 **A2／B2（已結案＋送醫，與正式報表同口徑）**
    算出雙向差集，印出「分母 ＝ 兩者都有 ＋ 只有 12 導程 ＋ 只勾 EKG檢查」的拆解，
    並把兩塊各寫成一份清冊。**順便修掉上面說的蓋檔問題**
- `tools/ems-report/ekgLists.test.mjs`：新增一項，釘住新清冊的大標與件數欄名
  （不可以跟「漏勾件數」混用，否則會拿錯清單去提醒同仁）
- `docs/TOOLS_SPEC.md` 3.12 改寫（升至 v1.18.6）：補上第 5 項、分母三塊的拆解式、
  兩份清冊各自對應「誰會少算」的對照表，以及「必須用 A2／B2」的理由

### 驗證
`node --test "tools/ems-report/*.test.mjs"` → 223 項全過。

## 2026-08-09　v1.18.3 解鎖回報「查無案件」，其實是頁面還沒載完就填了條件

### 問題描述
常駐監看（`unlock-watch`）收到一筆 2026-08-08 的解鎖工單，查詢期間是
2026-06-09 ~ 2026-08-09，案件明明落在期間內，卻回報
`查無案件：這個 TEMSIS 在查詢期間內沒有結果`。同一筆使用者手動操作可以正常解鎖。

### 根本原因
`navigation.mjs` 的 `gotoRecordQuery` 用「內容框網址是否含 AP 代號」判斷有沒有切到查詢頁。
但這套系統以 POST 導頁、網址常常不變，而且內容框**本來就停在救護紀錄表查詢那一頁**，
所以 `waitForContentAp` 的第一次檢查（不花任何時間）就成立了——
`link.click()` 剛送出、新頁面還在路上，程式已經宣告「到站」。

`out/watch.log` 留下的時間戳是鐵證：「查詢救護紀錄表」到「偵測到日期格式」只隔 **54 毫秒**，
連一次伺服器往返都不夠。

後果是起日、迄日、TEMSIS 三個條件全填在**即將被替換掉的舊文件**上（填完回讀也都正常，
所以完全看不出異狀），新頁面一抵達就把欄位洗成空白，接著按下 `#_btnQuery`
等於**拿一張空白表單去查詢**，自然零筆結果，再被翻譯成「查無案件」。

這是時序競賽，所以時好時壞：新頁面若在填欄位之前就抵達，那一輪就正常。

`gotoMenuItem`（進案件列表用）靠「網址有沒有變」判斷，有同樣的不可靠性。

### 修改內容
- `tools/ems-report/navigation.mjs`
  - 新增 `stampContent()`／`waitForContentReplaced()`：換頁前在文件上蓋記號，
    **記號不見了才算換好**（新文件的 `window` 是全新的，一定沒有記號）。
    換頁途中執行環境被銷毀、`evaluate` 拋錯時視為「還在換」，繼續等。
  - 新增 `waitForQueryFormReady()`：再確認 `#_txtFromDate` 真的出現才回傳，
    等不到就中止並說明原因，不在半載入狀態硬填條件。
  - `gotoRecordQuery` 改用上述判定（點選單路徑抽成 `clickRecordQueryMenu`），
    新增 `formReadyTimeoutMs` 參數。
  - `gotoMenuItem` 的「等網址改變」換成同一套記號判定。
- `tools/ems-report/navigation.test.mjs`（新增）：以假的 page／frame 釘住四種情境，
  其中最關鍵的是「**網址從頭到尾相同時，仍必須等滿換頁時間才回傳**」。
- `docs/TOOLS_SPEC.md`：1.4 加入「不可用網址判斷換頁完成」的通則、
  1.8 踩坑表新增一列、2.9 補上這次的實跑紀錄；版本升為 v1.18.3。

## 2026-08-07　v1.18.2 近期提醒的 7 / 30 天也改成工作日，全站單位統一

### 問題描述
提醒卡上顯示的是「剩 N 個工作日」，但**決定哪些業務會出現在卡片上的 7 天 / 30 天視窗，
以及卡片標題與展開按鈕上的「7 天 / 30 天」，都還是日曆日**。同一張卡片上兩種「天」，
使用者看到的數字和篩選用的數字對不起來。業務詳情頁待辦事項的橙色警示（3 天內）也是日曆日。

### 根本原因
v1.11.8 只把「顯示的剩餘天數」換成工作日，視窗門檻刻意留在日曆日（當時的理由是
「避免視窗被假日壓縮」）。但這個理由站不住腳：使用者要的就是「還有幾天能上班處理」，
視窗跟著工作日走才對得上。`REMINDER_DAYS` 三個值中 urgent 是工作日、default/expanded
是日曆日，同一個常數兩種單位，是誤解的來源。

### 修改內容
- `src/config/constants.ts`：`REMINDER_DAYS` 改名為 **`REMINDER_WORKDAYS`**（default 7 /
  expanded 30 / urgent 3），註解寫明三者單位一律為工作日。
- `src/lib/workday.ts`：新增 **`isWithinWorkdays(deadline, calendar, limit, from)`**。
  等同 `workdaysUntil() <= limit`，但一超過門檻就中止掃描——提醒卡每次渲染都要對所有
  未完成業務判定一次，明年才到期的業務不該為了算出精確天數逐日跑上數百圈。
- `src/lib/taskLogic.ts`：`getReminderTasks(tasks, withinDays)` 改為
  `getReminderTasks(tasks, isWithinWindow)`，視窗判定以函式注入。
  taskLogic 是純邏輯模組、不該依賴假日清單，workday.ts 又反過來 import taskLogic
  （會形成循環相依），注入是唯一乾淨的解法。
- `src/components/ReminderPanel.tsx`：改傳 `isWithinWorkdays(...)`；標題改「（逾期 +
  N 個工作日內到期）」、按鈕改「展開（30 個工作日）」/「收合（7 個工作日）」，
  按鈕文字改由常數產生，不再寫死。
- `src/lib/checklistLogic.ts`：`checklistDeadlineToneClass(deadline, calendar)` 新增假日
  清單參數，橙色門檻改用 `workdaysUntil()`（逾期紅色仍以日曆日判定）。
- `src/components/ChecklistSection.tsx`：以 `useHolidays()` 取得假日索引並傳給每一列。

### 副作用（預期行為）
跨連假時，7 個工作日的視窗會涵蓋較多日曆日（例如中間卡到三天連假就是 10 個日曆日），
提醒卡上的項目會比改版前多一些。這正是這次要的：提醒的單位是「還有幾天能上班處理」。

### 驗證
`npm run build`（tsc -b + vite build）通過，無型別錯誤。

## 2026-08-08　v1.18.2 監看要邊跑邊落檔，否則掉線了也查不出原因

### 問題描述
使用者回報「昨天到最後好像又斷線了，斷線的原因？」——**我答不出來**。

查得到的：
- node 程序從 8/7 09:01 一直活到 8/8（快 24 小時）→ **程式沒有死，v1.18.1 的修正生效了**
- `.auth/state.json` 最後保存於 8/7 09:02（初次登入）→ 掉線後沒有人再登入過，
  監看一直停在「等你回來登入」
- Windows 電源事件：**沒有任何睡眠／喚醒紀錄**，AC 電源設定為永不睡眠 → 排除電腦睡眠
- 雲端工單：只有 8/7 09:02 成功的那一筆，之後沒有新申請

查不到的：**掉線的確切時間與當下的徵狀**。

### 根本原因
`writeLogFile` 是**程式結束時**才寫的。監看還活著 → 紀錄還在記憶體裡 → 磁碟上仍是前一晚那份。
而監看被結束的方式多半是「直接關掉視窗」，那時也來不及寫。
等於**這個指令從頭到尾沒有可用的紀錄**，偏偏它又是最需要事後追查的一個。

### 修改內容

| 檔案 | 內容 |
| --- | --- |
| `logger.mjs` | 新增 `enableLiveLog(filePath)`：啟用後每一行**立刻追加**到檔案。用 promise 串接序列化，確保順序；**失敗一律安靜吞掉**——紀錄寫不進去不該影響正在進行的解鎖 |
| `config.mjs` | 新增 `PATHS.watchLogFile`（`out/watch.log`），與 `last-run.log` 分開：一個是結束時整份覆寫，一個是即時追加 |
| `index.mjs` | `unlock-watch` 一開始就啟用即時落檔，並在畫面上告知檔案位置 |

刻意用**追加**而不是覆寫：跨多次執行的歷史才留得住，
事後要查「前天半夜到底發生什麼事」時才有東西可看。

### 測試
新增 `loggerLive.test.mjs` 5 項（立刻落檔、帶時間戳、追加不覆寫、沒啟用時不亂寫檔、
落檔失敗不影響主流程）。工具測試共 **217 項通過**。

### 追加：落檔改為**同步**寫入
使用者接著把那個視窗關掉了，結果證實了這個洞的嚴重程度：
關視窗在 Windows 上是把程序硬砍，`last-run.log` **完全沒有被更新**，
scrollback 裡的掉線訊息就此消失。

因此把即時落檔從 `appendFile`（非同步）改成 `appendFileSync`：
非同步寫入若還排在佇列裡，程序被砍時會一起消失——而那幾行往往正是掉線當下最關鍵的訊息。
這個檔案一小時只寫幾行，同步寫入的代價可以忽略。

### 還沒有答案的事
這次掉線的原因**仍然不明**，只能排除電腦睡眠（Windows 兩天內沒有任何睡眠事件，
AC 電源設定為永不睡眠）。前一晚量到的是 6 小時 46 分，
下次掉線時 `watch.log` 會留下確切時間，累積幾次就能看出是絕對上限還是每日排程。

## 2026-08-07　v1.18.1 整夜實跑：心跳撐了 6 小時 46 分，但掉線後監看會自己結束

### 實跑結果（2026-08-06 整夜，試跑模式）
**心跳有效，該系統確實是閒置逾時。**

| 項目 | 結果 |
| --- | --- |
| 登入 | 00:06（本地） |
| 心跳 | 每 5 分鐘一次，**81 次全部成功** |
| 連續登入 | **6 小時 46 分**，中間完全沒掉線 |
| 掉線 | 06:53，心跳切頁時 `找不到名為 contentSidemenu 的 frame`（被踢回登入頁） |

06:53 很可能是系統每日重啟或絕對逾時上限，一次資料判定不了；再跑幾天若都落在同一個
時間點，就是排程性的、可以預期。

### 問題描述
掉線之後的行為是錯的：

```
06:53  心跳失敗 → 判定掉線
06:53  ⚠ 請在瀏覽器完成登入…
07:03  ❌ 超過 10 分鐘仍未完成登入 → 程式整個結束
```

凌晨掉線時使用者在睡覺，程式等 10 分鐘就退出。早上看到的是一個**已經死掉的視窗**，
而那之後完全沒有在監看。

### 根本原因
`ensureSignedIn` 直接沿用一次性流程的 `LOGIN_TIMEOUT_MS`（10 分鐘），逾時就拋錯，
一路往上炸掉整個監看迴圈。**那個上限是給「人就在電腦前」的一次性執行用的**，
套到常駐監看身上語意完全不對——常駐的正確行為是一直等。

### 修改內容

| 檔案 | 內容 |
| --- | --- |

## 2026-08-06　v1.18.0 常駐監看：有人送出申請就立刻處理，驗證碼只打一次

### 問題描述
使用者問：「電腦一直開著解鎖工單.bat，有人掛新的 TEMSIS 上去會立馬處理嗎？驗證碼怎麼弄？」
答案是不會——那支是一次性的，跑完就停在「按任意鍵關閉」。

### 為什麼原本沒做常駐
`docs/TODO.md` 原本就規劃常駐 worker，我在 v1.17.0 否決了，理由是登入會過期：
新工單來的時候多半已經掉線，要重新登入 → 要驗證碼 → 要人在電腦前，「常駐」省不到那個人。

**使用者指出該系統應為閒置逾時**。若是如此，定期做一次無害的操作就能讓登入不過期，
常駐就成立了——驗證碼只在最開始打一次。

### 做法

| 檔案 | 內容 |
| --- | --- |
| `unlockWatch.mjs` | **新檔**：監看主迴圈。每 20 秒問一次雲端有沒有新工單，每 5 分鐘切一次頁維持登入，每 30 分鐘報一次「還活著」（含已連續登入多久） |

| 捷徑 | `線上解鎖工單-自動監看.bat`（正式）、`不常用\線上解鎖工單-監看試跑.bat`（只維持登入不解鎖） |

### 這不是繞過驗證碼
驗證碼仍由使用者本人輸入過一次，之後只是**不讓那次登入過期**——等同自己開著分頁不關。
真的被伺服器踢掉時會停下來請本人再輸入一次，**絕不自動辨識**（TOOLS_SPEC 0.3 的鐵則不動）。

萬一系統其實有絕對上限、心跳擋不住，掉線時照樣會請本人重新登入，程式不會壞掉，

處理到一半被踢掉的話，後面每一筆都會得到「查無案件」——但那是因為根本沒登入，
不是案件真的有問題。照實寫回去的話申請人看到「需人工處理」，而實際上什麼事都沒發生。
因此每一筆看起來失敗時會多做一次登入檢查，沒登入就把工單**退回待處理**，下一輪再跑。

## 2026-08-06　v1.16.9 解鎖新增「無需處理」狀態：本來就沒鎖 ≠ 出問題

### 問題描述
使用者實跑 4 筆：3 筆成功解開、1 筆那張紀錄表本來就沒有鎖頭（已是未結案）。
程式卻寫成「共 4 筆：已解鎖 3 筆、**未處理 1 筆**」，那一筆還是用警告（⚠）呈現，
看起來像是有一筆出了問題。使用者要求把兩者在紀錄裡分開。

### 根本原因
狀態只有「已解鎖／已定位／需人工處理／查無案件／失敗」，沒有「不需要動作」這一類，
於是所有非成功的結果都被歸進「需人工處理」。但這兩件事的意義完全不同：

- **本來就沒鎖** → 正常結果，什麼都不用做
- **需人工處理** → 程式判斷不出來，要人接手

實際那一筆的判定路徑是：案件有 2 張紀錄表，第 1 張有鎖但 TEMSIS 不符、第 2 張沒鎖被略過。
案號是用該 TEMSIS 查出來的、案件不會錯，所以要找的那張只可能是沒鎖的第 2 張——
這是「不需要解鎖」，不是「不知道怎麼辦」。

### 修改內容

| 檔案 | 內容 |
| --- | --- |
| `unlock.mjs` | 新增 `無需處理` 狀態。三條路徑會回報它：①有鎖頭的都比對過都不相符、其餘本來就沒鎖 ②整件案子的紀錄表都沒鎖 ③沒有解鎖按鈕但看得到的紀錄表都沒鎖。紀錄裡改用一般訊息（不是警告）呈現 |
| `unlock.mjs` | 摘要改為「已解鎖 N 筆、本來就沒鎖 N 筆（不需動作）、**需要你接手** N 筆」；只有真的卡住時才提醒「請自行到系統處理」 |

**沒有解鎖按鈕**那條路另外補強：原本一律回報「可能已是未結案，或按鈕文字不同」，
現在會看紀錄表——都沒鎖就是 `無需處理`，連紀錄表都看不到才是真的有問題，
並附上該頁可點元素清單供排查。

### 順帶確認：新的解鎖判定在實盤上是對的
同一次執行的 3 筆成功案例中，2 筆兩個訊號都成立（訊息＋那一列鎖頭消失），
1 筆只有訊息成立——那筆的紀錄表**按之前就沒有鎖頭**，鎖頭訊號本來就不該成立，
判定邏輯（要求「本來鎖著、現在沒鎖」）運作正確。

### 測試
新增 5 項（三條 `無需處理` 路徑、打不開時仍須是需人工處理、摘要的三個數字要分開）。
另修正測試裡的一個錯誤假設：**沒有鎖頭的那一列一樣有「調整為未結案」按鈕**（實測）。
全部 **196 項通過**。

## 2026-08-06　v1.16.7 解鎖判定收斂為兩個訊號：鎖頭只認「按下去的那一列」，移除按鈕數量

### 問題描述

1. 鎖頭應該比對**點下去的那一排**變成「救護紀錄」，而不是全頁的鎖頭總數。
2. 「解鎖按鈕變少」這個訊號**永遠不會成立**（該按鈕解完之後不會消失），
   留著會不會反而造成誤判？

### 根本原因
第 2 點會。那個條件是「按鈕數變少就算成功」，平常確實不會成立，但**畫面被導走時會**：
連線逾時或系統跳錯誤頁時，解鎖按鈕會從 N 個掉到 0 個，「變少了」於是成立，
一件根本沒解到的案子會被報成已解鎖。既然它驗不到任何東西又會製造誤判，直接移除。

第 1 點是驗證的嚴謹度：全頁鎖頭總數變少只能說明「有某張被解開」，
不能說明解開的是不是你按的那張。

### 修改內容

| 檔案 | 內容 |
| --- | --- |
| `unlock.mjs` | `readLockState`（數全頁鎖頭與按鈕）改為 `readTargetRecord`：以**解鎖按鈕的序號**當錨點，用 `findPairedRows` 找出同一列的紀錄表連結，比對前後文字有沒有從「救護紀錄(鎖)」變成「救護紀錄」。按鈕序號可以當錨點，正是因為那個按鈕不會消失。按完之後讀不到那一列（畫面被導走）時一律不算成功 |

## 2026-08-02　v1.15.0 登入一次可沿用，短時間內再跑不必重打驗證碼

### 問題描述
使用者提出：驗證碼每次跑都要打，很煩，能不能改成由程式自動處理。

### 處理方式與取捨
**驗證碼自動辨識不做。** 那是來源系統用來確認「操作的是人」的機制，
把它自動解掉等於繞過對方的防自動化控制，這不是使用端能自行決定的事
（本專案自 `session.mjs` 建立起即載明此原則，TOOLS_SPEC 0.3 亦有）。

改為解決真正的痛點：**不必每一輪都重新登入**。

### 根本原因
每次執行都建立全新的 `BrowserContext`（沒有任何 cookie），
所以即使十分鐘前才登入過，系統一律視為未登入而再次要求驗證碼。
使用者本人其實已經解過驗證碼了，只是那個結果被丟掉。

### 修改內容

| 檔案 | 內容 |
| --- | --- |
| `tools/ems-report/config.mjs` | 新增 `SESSION_STATE`：檔案位置 `.auth/state.json`、保存上限 8 小時、沿用試探逾時 15 秒 |
| `tools/ems-report/session.mjs` | 新增 `loadSessionState` / `saveSessionState` / `clearSessionState` / `tryReuseSession`；`startSession(options)` 支援 `freshLogin`；登入邏輯抽成 `performLogin` |
| `tools/ems-report/index.mjs` | 新增 `--fresh-login`（任何指令皆可用），`withSession` 轉傳 |
| `.gitignore` | 新增 `tools/**/.auth/` |
| `scripts/make-portable.ps1` | 註解與訊息補上「不會複製 `.auth/`」 |
| `tools/ems-report/session.test.mjs` | 新增 9 個測試（總數 99 → 108） |

流程：進站後若帶著保存的狀態且**登入頁沒出現、主畫面 frameset 也建得起來**，
即判定沿用成功並跳過登入；否則安靜退回正常登入（刪舊檔、重新進站、本人輸入驗證碼）。
登入成功後寫一次檔，**關閉瀏覽器前再寫一次**（cookie 可能在這一輪被伺服器換過）。

### 安全上的處理
保存的 cookie 等同登入憑證，因此：

- 只寫到 `tools/ems-report/.auth/`，已加入 `.gitignore`；
- 可攜版打包只複製 `*.mjs` 與 README，天然不會帶走；
- 超過 8 小時即不再沿用（伺服器多半更早就讓 session 過期）；
- 狀態怪異時用 `--fresh-login` 強制重登。

### 驗證
`npm run tool:ems:test` 108 項全數通過。新增測試涵蓋：存讀往返、自動建資料夾、
檔案不存在、超過期限、內容毀損、重複刪除，以及 `tryReuseSession` 的三種情形
（登入頁還在／主畫面就緒／主畫面等不到）。

`TOOLS_SPEC.md` 升至 v1.15.0（0.3 表格、0.6 可攜版、**新增 0.8 節**、1.2 指令表、1.3 流程）；

## 2026-07-31　v1.13.0 新增「解鎖救護紀錄表」小工具（試跑版）＋可攜版打包

### 問題描述
使用者需要把指定 TEMSIS 的案件從「已結案」改回「未結案」，人工流程為：
救護紀錄表查詢（近兩個月＋TEMSIS）→ 開救護紀錄表抄下「救災救護指揮中心指派案號」→

一次要處理多筆時非常耗時，且容易點錯。

### 設計取捨
1. **本版只定位、不解鎖**：解鎖是不可復原的寫入動作，且案件列表、案件內部、紀錄表這三個畫面

2. **以畫面文字定位，不靠 id**：未探測過的頁面拿不到 id，且系統改版時 id 會變、文字不太會變。
   改用「找到標籤文字 → 取旁邊的欄位」這種近似人眼的方式（`pageFinder.mjs`）。
3. **多張紀錄表以「同一列」配對解鎖按鈕**：靠序號猜會解到別張，只有同一個 `<tr>` 才能確定

## 2026-07-28　v1.11.6 實作增減試算表的扣除，並修正 gid 導致的 HTTP 400

### 問題一：讀 Google 試算表回 HTTP 400
- **現象**：使用者填好網址後執行 `check-sheet`，紀錄檔顯示

> 讀第一個分頁；每一列若**時間落在查詢期間內**，就把該列的分隊**總案件數減 1**。
> 只扣分母——會列在該表單上的案件，本來就不會是系統中登記有到院前預警的案件。

### 修改的檔案與內容摘要
- `tools/ems-report/adjustSheet.mjs`：
  - `buildCsvUrl`：gid 為空時不帶參數（見上）。
  - `parseSheetDate`：容錯 `2026-06-01`／`2026/6/1`／`2026年6月1日`／後接時間／
