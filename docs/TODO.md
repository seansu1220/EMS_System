## 1. 驗證碼轉發：真正的「人不在電腦前也能解鎖」（2026-08-06 縮小範圍）

### 1.1 目前做到哪裡
原本第 1 項「用 iPhone 遠端執行解鎖」**已於 2026-08-06 實作**，但只做了一半：

| 原規劃 | 現況 |
| --- | --- |
| 手機開網頁下單 | ✅ 已完成（`/unlock` 解鎖工單頁，見 SPEC 2.8） |
| Firestore 當中繼 | ✅ 已完成（`unlockRequests` 集合，一個 TEMSIS 一張工單） |
| 電腦端接工單、逐筆回寫結果 | ✅ 已完成（`unlock-online` 指令，見 TOOLS_SPEC 第 5 章） |
| **驗證碼轉發** | ❌ **未做**——這是剩下的部分 |
| 電腦端常駐 worker | ❌ 已否決，改為手動雙擊捷徑（理由見 TOOLS_SPEC 5.3） |

因此現在的完整度是：**任何裝置都能提出申請、查結果，但實際執行仍要有人到電腦前打驗證碼。**
對「外出時想補解一兩筆」的情境，還差最後一哩。

### 1.2 要做的事
把 `session.mjs` 的登入改成可遠端接力：

```
電腦（worker）                     Firestore                    手機
 遇到登入頁，截下驗證碼圖  ──▶  captcha{image, askedAt}  ──▶  顯示圖片、輸入
 填入送出，繼續跑流程      ◀──  captcha{answer}          ◀──  送出答案
```

- **維持「驗證碼由使用者本人辨識」的原則**，絕不做自動辨識（TOOLS_SPEC 0.3）。
  使用者 2026-08-02 曾提議改為自動處理，**已明確否決**：那是繞過來源系統的防自動化機制。
- 超時（例如 10 分鐘沒回）要能安全放棄並關閉瀏覽器，不可讓瀏覽器一直開著。
- 答錯要能重來（系統會換一張新的驗證碼）。

### 1.3 為什麼可以先不做
**2026-08-02 起已有「登入狀態保存」**（TOOLS_SPEC 0.8）：若電腦在保存期限內已登入過，
遠端執行時根本不會出現登入頁，這一段就不會被觸發。
因此實務上的第一步應該是更省力的那個：**「沒有可用的登入狀態就直接回報 `needsLogin`、
請使用者到電腦前登入一次」**——可用性已經足夠，卻省下最難的一段。

### 1.4 前提：電腦要開著
驗證碼轉發做完之後，仍然需要**電腦開機、連著網路，而且有東西在監聽工單**
（現在是手動雙擊，沒有常駐程序）。也就是說這一項真正要用，前面還得補上常駐 worker，
而常駐 worker 之所以被否決正是因為 session 會過期——兩者其實是綁在一起的一組工作。

動工前先想清楚：**為了「偶爾外出時補解一兩筆」，值不值得養一個常駐程序 ＋ 驗證碼轉發。**
現成的替代方案見 1.5。

### 1.5 過渡方案（零開發，現在就能用）
iPhone 裝 Chrome Remote Desktop 或 RustDesk 連回電腦，直接點捷徑跑。
手機操作 Windows 桌面較不便，但零風險零成本；若只是偶爾要在外面補解一兩筆，用這個就夠了。

### 1.6 動工前必須先確認（**未確認前不要開始寫**）
| # | 待確認 | 怎麼確認 | 影響 |
| --- | --- | --- | --- |
| 1 | 單位是否允許以手機遠端操作公務系統 | 使用者自行確認 | **解鎖是會改動正式資料的寫入動作**，這是政策問題不是技術問題 |
| 2 | 外出時真的會用到的頻率 | 用一陣子現行版本再看 | 頻率低的話 1.5 的過渡方案就夠了，不必養常駐程序 |
