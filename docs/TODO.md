## 1. 用 iPhone 遠端執行「解鎖救護紀錄表」（構想，2026-08-01 提出）

### 1.1 需求
使用者希望人不在電腦前（例如外出、值班）時，也能用 iPhone 解鎖救護紀錄表。

### 1.2 為什麼不能直接在 iPhone 上跑
現有工具的核心是 Playwright 驅動一個**真的 Chrome** 去操作 `emsdt.tyfd.gov.tw`
（frameset 版面、圖片按鈕、PDF 另開視窗與下載）。而：

- iOS 不允許 App 以外的程式啟動瀏覽器行程，也沒有 Node.js 執行環境 → 無法跑 Playwright。
- Safari 內的 JavaScript 受同源政策限制，不可能跨網域操作別人的網站
  （這正是 [TOOLS_SPEC.md](TOOLS_SPEC.md) 第 0.2 節「為什麼不做在網頁上」的原因）。

**結論：iPhone 只能當「遙控器」，實際跑的仍是電腦。**

### 1.3 採用方案：電腦當 worker、手機開網頁下單
沿用現有的 Firebase 專案（Hosting + Firestore）當中繼，流程如下：

```
iPhone（現有網站新增一頁）        Firestore（中繼）              電腦（常駐 worker）
  貼上 TEMSIS，送出       ──▶  unlockJobs/{id} 建立    ──▶  監聽到新工作單，啟動瀏覽器
  顯示驗證碼圖、輸入       ◀──  captcha 欄位（圖）      ◀──  遇到登入頁，截下驗證碼上傳
  送出驗證碼              ──▶  captcha 欄位（答案）    ──▶  填入送出，繼續跑現有流程
  即時看到每筆進度與結果   ◀──  progress[] / results[]  ◀──  逐筆回寫（日期／車輛／狀態）
```

**關鍵優點：實際連線仍由電腦發出，個案明細（紀錄表全文、PDF）不經過雲端**，
維持 TOOLS_SPEC 0.3 的個資保護總則。雲端只走「工作單 + 進度 + 結果摘要」。

### 1.4 為什麼不整包上雲（Cloud Run + headless Chrome）
評估後**否決**，三個理由：

1. 必須把消防局系統的帳號密碼放到雲端主機上。
2. 個案資料會流經雲端，推翻現行「紀錄表全文只存記憶體、用完即棄、只顯示末 4 碼」的設計。
3. `emsdt.tyfd.gov.tw` 是否允許任意來源 IP 連入無法確認；若有來源限制，此方案直接不成立
   （方案 1.3 不受影響，因為連線是從使用者自己的電腦發出的）。

### 1.5 動工前必須先確認（**未確認前不要開始寫**）
| # | 待確認 | 怎麼確認 | 影響 |
| --- | --- | --- | --- |
| 1 | 系統從外部網路連不連得到 | 用手機 4G/5G（不接辦公室 Wi-Fi）開 `https://emsdt.tyfd.gov.tw` 試登入 | 連不到也不影響本方案（連線由電腦發出），但會影響日後任何雲端化的可能 |
| 2 | 單位是否允許以手機遠端操作公務系統 | 使用者自行確認 | **解鎖是會改動正式資料的寫入動作**，這是政策問題不是技術問題 |
| 3 | 解鎖流程本身是否已實跑驗證通過 | 見 [TOOLS_SPEC.md](TOOLS_SPEC.md) 2.10「待實跑確認的項目」 | 本機都還沒確認正確前，不應該再加一層遠端 |

### 1.6 實作拆解（預估由多到少）
1. **電腦端 worker**（`tools/ems-report/worker.mjs`，新檔）
   - 常駐監聽 Firestore 的待處理工作單；一次只跑一筆，跑完才取下一筆。
   - 沿用現有 `runUnlockFlow()`，**`unlock.mjs` 本身幾乎不用改**——
     只需把「終端機輸入輸出」抽換成「Firestore 讀寫」。這正好是專案的職責分離原則：
     現有的 `promptTemsisList()`（輸入）與 `printUnlockSummary()`（輸出）就是要被替換掉的兩端。
   - 以服務帳號金鑰（`tools/ems-report/.env`，已 gitignore）連 Firestore，**金鑰不得進版控**。
2. **驗證碼轉發**（最花工夫的一段）
   - `session.mjs` 目前是「開有頭瀏覽器，等使用者本人在電腦前輸入驗證碼」。
     遠端模式要改成：截下驗證碼圖片 → 上傳 → 等手機回填 → 代為填入送出 → 失敗可重來。
   - **維持「驗證碼由使用者本人辨識」的原則**，絕不做自動辨識（TOOLS_SPEC 0.3）。
   - 超時（例如 10 分鐘沒回）要能安全放棄並關閉瀏覽器。
3. **手機端頁面**（`src/pages/` 新增一頁，走現有路由與權限）
   - 貼上 TEMSIS（沿用一次可貼整欄的處理）、顯示驗證碼輸入框、即時進度、結果列表。
   - 結果列表比照終端機摘要：**案件日期／出勤車輛（分隊）／TEMSIS 末 4 碼／狀態／說明**。
4. **Firestore 資料模型與安全規則**
   - `unlockJobs/{id}`：{ status（queued/running/waitingCaptcha/done/failed）, temsisList[],
     dryRun, captcha{imageBase64, answer, askedAt}, progress[], results[], createdBy, createdAt, finishedAt }
   - 安全規則：**僅管理員可建立與讀取**（比照 `holidays` 的寫入限制）；worker 以服務帳號存取。
   - 規則要一併加進 `scripts/rules.test.mjs` 的測試。

### 1.7 必須留意的取捨（實作時不要迴避）
- **TEMSIS 編號會落到 Firestore。** worker 需要完整編號才能查詢，無法只存遮蔽值。
  因此：工作單**完成後即刪**（或設短 TTL）、規則限管理員、**只存編號與狀態，不存紀錄表內容**。
  這一點與 TOOLS_SPEC 0.3「不上雲」是有出入的，屬於為了遠端操作而做的**明確讓步**，
  實作時必須在 TOOLS_SPEC 補上這個例外說明，不要當作沒發生。
- **電腦必須開機並連著網路**，否則工作單只會排在佇列裡。手機端要能看出「worker 沒在線」。
- 解鎖仍應維持**預設試跑**；手機端要真的解鎖必須有明顯的二次確認，不能一鍵誤觸。

### 1.8 過渡方案（零開發，現在就能用）
iPhone 裝 Chrome Remote Desktop 或 RustDesk 連回電腦，直接點捷徑跑。
手機操作 Windows 桌面較不便，但零風險零成本；若只是偶爾要在外面補解一兩筆，用這個就夠了。
